# Next local evaluation

Recommend a bounded generative scene/relation comparison before another search entry point. The current app already exposes local text, Content, confirmed names, self selection and nearby composition; its most consequential uncertainty is whether a small VLM improves difficult visual queries enough to justify its cost. This advances PL124/PL125, not completion of G4: cloud comparisons, physical hardware and final held-out evaluation remain outside current emulator-only/no-hosting authorization.

## Existing inputs and boundaries

- docs/model-and-evaluation-plan.md requires generative comparison. docs/large-gallery-evaluation.md records the 2,000-image baseline and explains why generated conjunction probes do not establish useful personal-query quality.
- .benchmark-data/gallery-v1/manifest.json freezes originals, hashes, source/license metadata, splits and positive/negative category/relationship annotations. app/build/large-gallery-benchmark/emulator.json contains actual CLIP rankings. tools/large-gallery/report_results.py separates explicit negatives from unjudged images.
- .benchmark-data/vlm-smol500m/acquisition.json pins the Q8 SmolVLM2-500M/projector pair, totaling 545,593,888 bytes. Licenses and model cards are beside them. .agent-staging/vlm-eval/native-build-receipt.json identifies the locally compiled Windows llama-mtmd-cli executable and pinned source commit 9048bad8d6e3a0f9f1726e238e451181c7e02613.
- app/build/vlm-host-smoke.json shows exactly one image generated a description successfully. It establishes host loading/inference only; no Android speed, retrieval gain or factual accuracy is established. The staging README now distinguishes its historical pre-build text from the later receipts.
- Actual application boundaries are semantic/ClipModel.kt, library/PhotoContentSearch.kt, subjects/PhotoQueryPlan.kt and library/PhotoQueryExecution.kt. app/build.gradle.kts currently has ONNX/LiteRT dependencies and no native VLM/JNI integration. The missing toolchain prerequisite has now been resolved separately: official NDK r30 is checksum-verified under D:/Android/ndk/android-ndk-r30, with a small publisher-digest-verified Ninja runtime in external staging. .agent-staging/vlm-eval/android-ndk-acquisition.json and ninja-1.13.2.json record the exact artifacts. Cross-compilation and native emulator inference remain pending; they are deliberately held while the root's timed CLIP baseline runs. No additional model checkpoint was acquired.

## Ordered work and acceptance

| Step | Depends on | Concrete deliverable and bounded acceptance |
| --- | --- | --- |
| 1. Freeze useful judgments | Existing corpus/CLIP baseline | Freeze 20 ordinary scene/relation queries and 4 difficult combination probes, with visually similar wrong-relation/wrong-person-color examples. A probe is not known absent from the gallery. Use a separate reviewed validation cohort to refine prompts, and freeze the held-out evaluation cohort before VLM outputs. Inspect the fixed top 8 candidates in deterministic shuffled order with baseline scores/ranks hidden; record relevant/irrelevant/unjudgeable plus source/license IDs. Existing missing annotations are not negatives. If a second human review is unavailable, label judgments provisional and record whether the reviewer was AI; AI agreement is not independent human truth. |
| 2. Qualify Android execution | Pinned source/model; actual NDK and sufficient disk | Cross-compile the pinned llama-mtmd-cli target for emulator x86_64, API 30, CPU-only, with mtmd enabled and network/video subprocess dependencies disabled. Use the pinned tools/mtmd and docs/android.md instructions from the local source; verify the produced ABI/libraries. Push only to the emulator and run three existing public images under a fixed image/context/token/thread budget. Preserve output, exit status, hashes, peak process memory and end-to-end cold duration. A timeout, incompatible operation or OOM is a recorded feasibility failure, not a substituted host result. |
| 3. Compare equal candidate sets | Steps1–2 | Keep the existing baseline's top 8 for every query; VLM reranks that same set or abstains. Cap the evaluation at 192 query-image decisions, one image per request, at most 96 generated tokens and two CPU threads. Initially use explicit question/short answer with strict parsing; malformed/uncertain outputs abstain rather than silently mapping to yes. Measure CLIP baseline and VLM on identical candidate pools; separately report relevant images missed by first-stage CLIP that no reranker can recover. Do not compare VLM top 8 with CLIP's full catalog as if they had equal coverage. |
| 4. Measure actual cost and errors | Step3 | Report paired top 1/top 5 success, judged precision and unjudged counts, absent-query false suggestions, relation/color errors, hallucinated identity/place/text and abstentions. Include image preprocessing, model/projector loading, vision encoding and decoding, cold versus resident-model latency, peak RSS/PSS and process failures. CLI reload-per-image time is cold time; claim warm latency only after a resident session actually runs. Weights alone are not peak memory or index size. |
| 5. Decide minimal app integration | Quality and cost from step4 | Ship no model change merely because inference succeeds. A positive result requires a predeclared useful gain on the reviewed hard queries without hiding absent-query regressions, and acceptable observed resource cost. Otherwise document a rejection or narrower capability. For a promising candidate, add a small replaceable local image-answerer adapter behind PhotoContentSearch; preserve existing confirmed identity/GPS restriction before any VLM call and keep generated judgments partial. Implement native handle ownership, cancellation, token limits, source/model versioning and stale-publication tests before enabling a user workflow. |

This initial comparison should stream owned inputs and bounded outputs, never load the full gallery or persist a second image copy. The model pair adds roughly 520 MiB of optional evaluation weights, already acquired; do not automatically add it to the roughly 300 MiB production package. Store no VLM captions in the main index for the experiment. If enrichment later proves useful, version and encrypt bounded records with the same edit/delete/revocation guarantees as other derived evidence, and measure the complete index footprint.

No VLM prediction can create a person/object confirmation, identify the phone owner, assert Surat from a street scene or change upload consent. Image text remains untrusted input with no tools or actions. The current three processing modes remain planned, but this run is LOCAL only. Emulator throughput and memory are emulator results; battery, thermals and low-end ARM suitability remain unqualified. Completing a fair local pilot is useful even if deployment is rejected.

The final frozen protocol and visual relevance rules are recorded in [relation-vlm-pilot.md](relation-vlm-pilot.md). Candidate judgments join back to the immutable baseline by image ID; shuffled presentation order is never treated as baseline rank. Keep all 20 ordinary queries in top-one/top-five hit denominators and report unjudgeable cases separately. Report the number of fully irrelevant reviewed combination pools: if zero qualify, the absent-pool safety criterion is unproven, not passed. Glasses/sunglasses/goggles and other shared-image families are correlated; report family and image overlap rather than treating 24 queries as independent trials.
