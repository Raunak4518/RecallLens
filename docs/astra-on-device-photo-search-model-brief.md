# Research brief for GPT‑6.2 Astra
## Designing better on-device semantic photo search for Android

### Your assignment

Design a stronger on-device photo retrieval system for an existing Android app. A user with thousands of photos enters one natural-language prompt. The system should find the intended photos even when the prompt mixes visual content, fine details, personally named entities, remembered text, and context. It should return useful results within a few seconds once the relevant evidence has been indexed. It should get more useful as the device processes the library and as the user confirms or corrects results.

Treat this as an applied ML, information retrieval, and mobile inference problem. Diagnose the current pipeline and propose practical alternatives with experiments that could disprove your assumptions. Keep the parts that are already good and identify exactly which current components you would replace, augment, or remove. Original combinations of methods are welcome. A published technique with a clear advantage is equally useful. Provide a concrete baseline, a recommended design, and a more ambitious design with a clear reason to pursue it.

The rest of this document gives you the implementation and measurement context. You can answer using this brief alone. The linked repository files are for verification if you also have the checkout. Treat proposed capabilities and research questions as open work.

## 1. What the system must achieve

- **One prompt, mixed intent.** Users should be able to describe what they remember in their own words. Resolve the intent internally. A query might describe an object category, a specific instance, a person, a region, a text fragment, a document class, a relationship, a time or place, or some combination.
- **Rank by how well each result answers the whole prompt.** The highest-ranked results should satisfy the important parts together. Results with weaker or incomplete evidence may be useful as additional candidates, as long as their ordering and interpretation reflect the missing evidence. Separate a high semantic score, a model-suggested identity, and an identity the user has actually confirmed.
- **Learn private names and references.** People, objects or other subjects can have user-defined names and aliases. Search should be able to combine a named entity with other conditions. Preserve the existing confirmed-only policy for Named search. More photos may be suggested for review. In mixed prompts, distinguish an established identity from uncertain resemblance.
- **Make search useful while the library is being indexed.** Reuse persisted evidence. Prioritize work that makes more of the library searchable sooner and deepen coverage incrementally. A search should not routinely decode the library or restart expensive inference. An absent result in a partially processed library carries a different meaning from an absent result after the applicable evidence is ready.
- **Operate on the phone.** Android first, with a current minimum of Android 11 (API 30). The core system should work offline on locally available photos. Keep photos and derived personal learning on the device. Include model weights, runtime memory, persistent derived data, decoding and indexing compute in your design. The project tolerates a useful index in the low hundreds of MB on large libraries, but asks you to justify it in bytes per photo and per region. A copied gallery or a multi-GB mandatory model stack defeats this goal.
- **Evaluate at realistic scale.** Use at least 10,000 distinct real images for the large-gallery test. Add dedicated cohorts for rare and difficult cases. Evaluate physical ARM phones before making production claims. Treat an interactive end-to-end warm p95 of roughly 3 seconds as an initial design target to validate. Report first search after startup, first usable results during indexing, and initial-library processing separately.
- **Keep models replaceable.** Experiment with OCR, visual embeddings, detectors, identity encoders, parsers and rerankers independently on shared fixtures. Propose contracts and migration rules so a better model can be trialed and rolled back. Avoid making every modality mandatory for every photo.
- **Scope.** Cover model choice, data representation, inference, scheduling, retrieval, ranking, local feedback and evaluation. Treat Android and encrypted storage as design constraints. There is no request here to redesign the app UI, build a cloud system, or propose an account or deployment architecture.

## 2. Current implementation

| Capability | What the Android app does today | Where to look for headroom |
| --- | --- | --- |
| Whole-photo visual search | Uses a bundled quantized ONNX CLIP ViT-B/32 image and text encoder. Stores a 512-dimensional representation per image, encodes queries, and compares normalized embeddings. Supports selected-photo similarity. The model revision specifies an 896-pixel maximum source decode edge and the vision preprocessing uses a center crop. The text tower has a 77-token context and its frontend truncates the input to 512 characters. | Whole-image similarity loses position and fine detail. Center cropping can remove the queried region. One vector must represent many independent subjects and relationships. |

The existing max-edge setting is 1,600 pixels and extraction is bounded to 256 lines and 16,384 characters. Filenames can supply separate evidence. | Missing characters, downsampling and line breaks can make a recognizable photo irretrievable. Unconstrained fuzzy matching can make IDs, classes and other easily confused values unreliable. |
| Document understanding | A targeted marksheet matcher combines title, class, candidate and year clues. This is a narrow route over recognized text. | Generic document typing and field-aware retrieval are open problems. A relevant document can share most of its boilerplate with a different class or version. |

Prompts mentioning an unsupported detail can still yield a strong global score. |
| Indexing and cache | WorkManager coordinates staged work. The app publishes and persists visual results before the slower OCR pass in the production coordinator. Encrypted stores retain model evidence and references for reuse. Face/object records load on demand where applicable. | Models run at different rates. Test staged inference, region reuse, selective expensive passes and cache-version migration against actual launch, search and thermal behavior. |
| Candidate models | PP-OCRv6 Tiny, SigLIP 2 and SmolVLM2 were evaluated in specific benchmark paths. The important experimental distinction is **candidate coverage versus ranking**. A correct photo can be missing because evidence was never extracted, because its stage has not run, because the candidate pass never surfaced it, or because the final score demoted it. ## 4. Generalized failure situations to solve

Treat these as families of evaluation problems and draw many test queries from each. The system should make progress across the families without turning into a growing catalogue of one-off prompt rules.

| Problem family | Where a system like this loses the answer | How to isolate the failure |
| --- | --- | --- |
| Unpredictable wording | Different people describe the same evidence with slang, shorthand, spelling variants, mixed scripts, paraphrases, and indirect references. Long prompts can exceed a model's token budget. | Group paraphrases by intended meaning. Test literal, colloquial, multilingual and reordered versions. Compare query plans and ranked candidates. |
| Ambiguous intent | A phrase can denote a broad category, a personal identity, a place, an event, a document type, or actual text. A planner that chooses one route too soon can lose the answer. | Label plausible interpretations. Compare a single confident route with multiple bounded hypotheses. Check whether intent confidence corresponds to outcomes. |
| Compositional retrieval | Dense image–text models can reward individual terms without connecting them. A photo can contain all requested elements while failing their specified relationship. | Use shuffled-relationship and attribute-binding hard negatives. Measure recall at candidate depth separately from correct ordering of otherwise similar images. |
| Spatial and directional constraints | Relative position, ordering, proximity, occlusion, foreground/background, and viewpoint often vanish in a global vector. | Pair photos with the same visible categories and different arrangement. Require localization and score each relation independently of category presence. |
| Fine visual attributes | Pattern, materials, shape, markings, color shades, small accessories, or parts can be lost when the whole photo is resized or cropped. | Annotate size and visibility of the region. Compare global inference, region pooling, multiscale crops and deferred detail inference. Include cropped-away positives. |
| Attribute-to-entity binding | A scene may contain several people or objects. A color, pose, state or accessory can be assigned to the wrong one. | Use photos with multiple plausible bearers. Check whether the predicted attribute and region identify the correct subject, not merely any occurrence. |
| Depiction versus subject | Screens, posters, graphics, overlays, filters, reflections, thumbnails and illustrations can contain recognizable visual content without depicting the requested real-world scene. | Label depiction medium and relevance separately. Include both cases where a depiction is a hard negative and cases where it is exactly what the user wants. |
| Action and scene state | Near-identical images may differ by what is happening, lighting, weather, time-of-day appearance or the state of an object. Camera processing and edits change these cues. | Match images on overall scene and vary the intended state. Separate visually verifiable states from states that need metadata or are unknowable. |
| Person identity | Face size, pose, age, occlusion, low light, strong resemblance and group shots can undermine detection and matching. Clothing and body cues are context-dependent. | Measure detector coverage and identity performance separately. Include held-out people, negatives and cross-session comparisons. Test consistency across faces within one image. |
| Clustering and user naming | Similarity chains can merge different subjects. One subject can split across many clusters. A single mistaken merge can propagate bad labels over a gallery. | Report pairwise precision/recall and per-entity cluster quality, plus merge and split errors. Compare single-reference matching with multiple diverse confirmed references and conservative clustering. |
| Exact non-person identity | Instance retrieval is harder than classification. Visually similar manufactured objects, replacement items, edits and changed appearance defeat simple cosine ranking. Reference-free ownership is underdetermined. | Use same-design impostors, independently captured positives, changed views and items with little observable distinction. Require a separate unknown outcome and inspect candidate recall versus acceptance. |
| Other persistent entities | A place, recurring group, document, meme or item of clothing has different identity criteria. A group may change membership. A meme can be the same template with different text. A document may be the same physical page or the same form type. | Define what identity means for each kind. Test stable references, near neighbors, changed content and whether the user requested a type, instance, version or group. |
| OCR perception | Small or stylized text, compression, curvature, blur, perspective, contrast, mixed scripts, glare and crowded layout can leave a required term absent before any search happens. | Annotate visible regions and readable text. Calculate region recall, character/word error and target-query retrieval by quality band. Include photos where the desired text is unreadable to a human. |
| OCR retrieval | Reading order, scanning artifacts, broken spans, OCR confusions, OCR variants and text spread over multiple lines can block exact search. Overly fuzzy lookup can merge closely related identifiers. | Rerun retrieval with human transcripts, saved OCR, and controlled OCR noise. Compare exact, lexical fuzzy, and character-aware results while tracking false acceptance of short sensitive fields. |
| Document class and field semantics | Two forms can share headers and vocabulary. Someone may remember a field or edition indirectly. A name, number or year has different meaning depending on where it appears. | Hold out document families and layouts. Use field-aware positives and hard negatives that differ in one required field. Test when image appearance should outrank low-quality OCR and when exact fields must determine the order. |
| Time and event understanding | Capture, import, edit and receive times can disagree. Recurring or movable events, local calendars and vague time phrases can expand the set of plausible dates. | Introduce delayed imports and repeated events. Evaluate visual-only, time-only and fused variants, including when one source is missing or unreliable. |
| Place and environment | Names are ambiguous, boundaries are fuzzy, locations can be nearby, and most images give incomplete evidence about place. GPS may be unavailable or contradict context. | Test locally nearby positives, visually similar remote negatives, duplicate place names, absent GPS and imprecise queries. Measure whether a soft distance prior improves search. |
| Subject drift and personal history | Names and personal relationships change over time. A label may refer to different places or objects in different periods. Repeated reference updates can overwrite useful history. | Simulate dated alias changes, multiple simultaneous references, and explicit user correction. Compare recency priors with effective time windows and versioned references. |
| Duplicates and derivatives | Bursts, reposts, crops and edits dominate top results, crowding out distinct matches. Deduplication can also hide the specific edit or text variation the user wants. | Judge near-duplicate families and individual variants. Measure diversity and recall for both broad searches and exact-version searches. Keep source-group splits when training. |
| Open-set searches and confidence | The desired photo, entity or detail may be absent. A nearest-neighbor method still has a highest score. Scores from different models may be incomparable. | Include absent-target queries and strong impostors. Plot risk versus coverage, confidence calibration and false accept rates at rising gallery sizes. Separate unknown evidence from a verified mismatch. |
| Partial, stale and inconsistent evidence | A photo can be searchable visually before its text or local regions exist. An edit or re-index can make pieces refer to different versions. Some media has missing metadata or poor resolution. | Repeat the same queries across processing states and simulate asset and model-version changes. Check whether early ranking remains useful and whether stale evidence can still influence a result. |
| Scale, resource contention and generalization | A new encoder can improve isolated top-k scores while making a library unusable under actual phone load. Tail behavior changes with the number of similar images and the mixture of content. | Measure broad and difficult queries during idle search, active indexing, cold startup and sustained operation. Separate host, emulator and real ARM results. Measure cost per new modality. |

### 4.1 Error taxonomy for every measured miss

For every judged query where the desired photo is absent or ranked too low, record the first actionable cause and competing causes. At minimum distinguish:

1. Missing, unreadable, or unobservable information in the source. Define what a well-informed human could verify from available evidence.
2. The photo is not searchable yet for the needed modality, or the evidence is stale.
3. The query was parsed into the wrong intent, entity, constraints or time context.
4. The right content was visible but the corresponding detector, cropper, OCR, segmenter, metadata reader or encoder failed.
5. The right evidence existed but the correct candidate was dropped by retrieval, candidate limits, hard filters or overly aggressive deduplication.
6. The candidate survived but lost in evidence fusion, relation reasoning, normalization, calibration, personalization or reranking.
7. The query is ambiguous enough to admit additional relevant photos, and adjudication is incomplete.

Use several oracle interventions on the same cases. Supply the gold query plan, gold crop, gold text or metadata, or force the gold item into candidates one at a time. Report the incremental improvement. These experiments tell us where additional inference can pay off and what the best possible reranker could do with current recall.

## 5. Design questions Astra should resolve

### 5.1 Architecture and model choice

Develop and compare three viable variants: a calibration and retrieval baseline that reuses the current encoders, a lightweight architecture you would build next, and a higher-cost challenger with a specific measurable advantage. Explain your recommended path end to end with a diagram and candidate flow. For each design, specify the responsibilities of each model, which stages are optional, persistent evidence, interactions between modalities, and how quality degrades when individual models are unavailable.

- Compare better global encoders, a small detector plus region embeddings, text-conditioned localization, selective tiled inference, visual token late interaction, and a bounded cross-encoder or VLM. Quantify the region-multiplication and query-time costs rather than counting only model parameters.
- Get a serious lightweight baseline from existing stored features and small improvements first. Compare lexical-plus-dense retrieval, rank fusion, calibrated scoring, reranking a small subset and explicit relation checks. A fusion baseline should expose when a gain comes from adding evidence versus changing scores.
- Explain which parts genuinely need learned models and which can use typed evidence, normalization, compact indexes, metadata or structured rules. Consider learning a small query router, region policy or ranking head before proposing end-to-end retraining.
- For each named model candidate, verify the exact checkpoint or conversion, license, quantization and supported operations. Give plausible Android runtime and fallback options, and distinguish a measured result from a cost estimate. Include loading and tokenizer/model initialization. Explain what would rule the candidate out before an expensive port.
- Evaluate VLMs in at least two bounded roles if plausible: selective background enrichment and bounded query-time reranking. Compare them on the same residual errors to improved global and region baselines. Check per-constraint correctness, hallucination, output stability and elapsed time. Propose exclusion from the shipping path if the evidence fails.

Starting research references for comparison: [original CLIP paper](https://proceedings.mlr.press/v139/radford21a.html), [ARO compositional evaluation](https://arxiv.org/abs/2210.01936), [SigLIP 2](https://arxiv.org/abs/2502.14786), [FG-CLIP](https://arxiv.org/abs/2505.05071), [ONNX Runtime execution providers](https://onnxruntime.ai/docs/execution-providers/). Verify benchmark relevance, model availability and phone feasibility independently.

### 5.1.1 Hypotheses worth testing against the current baseline

Use these to start the search for a better design. They are hypotheses, with simple experiments to reject them. You can replace them with better proposals.

| Hypothesis | Cheapest useful comparison | Why it could fail |
| --- | --- | --- |
| A compact per-photo summary of multiple views improves candidate recall enough to defer higher-resolution verification. | Compare the global vector with a second global view, a fixed small number of pooled regions, and sparse selective regions under the same byte budget. Evaluate tiny foreground/background regions and multi-subject scenes. | Additional views can duplicate scenery, amplify false positives, or make persistent costs scale with clutter. |
| The system should spend extra inference only on uncertainty that can change the top results. | Replay baseline rankings and run one specialist selectively when a requested condition is unresolved. Compare with applying the same specialist to the full top-k, and with a score-margin rule. Measure recovered hits per second and residual false accepts. | The right image may never reach the shortlist, the uncertainty signal may be unreliable, or the limit may favor common query types. |
| A small, explicit model of regions and their relationships outperforms a larger global encoder on compound requests. | Hold the candidate pool fixed. Compare a global ranker against region, relation and hard-negative features, then against a compact learned or generative verifier. | Detector coverage may cap gains, matching multiple ambiguous regions may be slow, and the known relations may be too narrow. |
| Prototype sets or calibrated exemplars improve exact-instance suggestions without training a new encoder. | Compare the nearest single example, a mean embedding, a bounded set of diverse exemplars and a score accounting for the strongest impostor. Use independent capture sessions and absent identities. | Few confirmed examples can represent backgrounds or camera viewpoints instead of the subject. A changed object can make tight prototypes brittle. |
| A stronger teacher can improve a small student or routing policy on a measured residual task. | Annotate a compact validation cohort, compare frozen student features before and after a small head trained on separately labeled data, and compare with the teacher alone. | Teacher labels can encode the same errors, extra training may not beat rules, and gains may vanish on held-out identity and image sources. |

For each promising hypothesis specify what signal survives to the encrypted index, what is recomputed at query time, and whether success would change the architecture or just one policy. Search for better architectures before choosing model weights.

### 5.2 Query planning, candidate generation and ranking

- Show a typed representation for a query with multiple possible interpretations. Include required, preferred and uncertain conditions, entities, relationships, negative evidence and provenance. Define how you recognize a literal phrase versus remembered meaning, and when clarification is valuable or avoidable.
- Specify candidate generation with retrieval depth budgets. Compare union, intersection and staged retrieval. Preserve candidate recall when a high-priority modality is still being indexed. Describe which signals can be trusted as hard constraints and which should rank softly.
- Define how a confirmed named entity, an unconfirmed similarity, a missing OCR observation, and a contradictory observation each affect scoring. Preserve established Named results and explain what evidence could legitimately outrank them on a mixed prompt.
- Define rank fusion or scoring in pseudocode. Explain how you avoid double-counting correlated semantic models, arbitrary cross-model comparison and large cohorts dominating results. Design a small set of understandable reason codes.
- Provide a practical policy for enough results: high-evidence matches first, additional candidates when useful, and a credible empty outcome for absent targets. Specify how candidate diversity interacts with near-duplicates and related instances.
- Compare how dates, text, metadata and visual cues should affect rank when they disagree, including photos received later, edits and low-confidence OCR. Distinguish evidence classes that need field-level exactness from ones where fuzzy meaning helps.

### 5.3 Entity discovery, linking and safe personalization

- Propose a flow for model-detected regions to become reviewable entity groups. Define quality checks, indexing eligibility, clustering/linking method, group representations, evidence provenance, and prompt-time entity resolution. Compare a single global clustering pass with incremental linking and on-demand suggestions.
- Separate broad category detection from exact-instance similarity. Compare whole-image, cropped and part-based embeddings. Study exemplar diversity, background leakage, precision versus group coverage, and how many exemplars are needed before automatic proposals improve. Treat same-design ambiguities as real uncertainty.
- Define suitable invariances by entity type. Faces, manufactured objects, groups, garments, locations, documents and media derivatives need different criteria. Use the simplest shared storage and retrieval contract that can express their differences.
- Include merge, split, reference removal, alias/date changes and correction. Describe how these update derived personalization without rebuilding unaffected model evidence. Keep irreversible auto-label propagation out of a first version.
- Specify when a candidate can be recommended for review, when to abstain, and what to display for unidentifiable details. Compare deterministic thresholds, gallery-adaptive decision margins, short calibrated heads and per-entity prototypes with validation support.


### 5.4 OCR and specialized detail extraction

Propose a path for OCR that is fast enough to run broadly and accurate enough to recover rare details. Explain how you would prioritize likely text regions, reject low-value repeated inference, identify failed or uncertain extraction, and schedule a stronger recognizer, a higher-resolution crop or a different script package only where justified. Keep an uncertainty-aware route for apparently textless images. Permanent skipping needs evidence against a clearly stated miss budget. Compare detection/recognition swaps independently. For OCR search, compare field-level exactness and robust fuzzy matching using the same candidate pool. Use document layout or small classifiers if they measurably distinguish visually and lexically similar types.

Discuss when the same mechanism applies to other fine details. An index could store a small amount of coarse evidence broadly and deeper evidence for promising regions. Explain how such regions are selected before a user asks, how new or unusual queries obtain missing evidence, and how confidence should change when the evidence is unavailable.

### 5.5 Android inference and storage

- Design a schedule for progressive availability. Compare a quick visual pass plus deferred specialists, an interleaved schedule that makes some text searchable earlier, and resource-aware overlap. Make separate throughput, time to first useful results, and tail-latency predictions. Identify break-even cache and batch sizes.
- Give a plan for minimizing input decode and model initialization. Review shared decode, resolution selection, crop reuse, batching, model session reuse, thread limits and peak RAM. Distinguish what can share the same resolution and what cannot. Account for background indexing competing with a foreground query.
- Compare CPU execution with Android hardware acceleration based on operator support and device measurements. Include mixed backends, unexpected CPU fallback, quantization regressions and execution consistency across device tiers.
- Estimate a storage budget for 10,000, 25,000 and 50,000 photos, with a documented region-count distribution and measured or bounded overhead. Include weights, persisted data, database/page overhead, OCR postings, metadata, region embeddings, startup caches, temporary files and compaction. Compare compressed or quantized features with a full-precision reference on the same queries.
- Compare a dense exact scan with a compressed or approximate index at realistic scales. The current 10,000-vector ranking baseline is fast. Explain the scale and number of region vectors at which a more complicated index would pay off. Include index update, rebuild, recall loss and migration costs.
- Design incremental and interruptible indexing with model/data version signatures. Explain how each modality can recover after cancellation, reprocess just its changed inputs, coexist with an older cache during an update, and bound work after a device is idle again. Separate indexing costs from cached search costs in the measurement plan.

## 6. Continuous improvement on the phone

Design three improvement loops. Each loop should have measurable costs, a clear trigger, and a safe fallback.

| Loop | What may change | What to prove |
| --- | --- | --- |
| Progressive evidence | Add cached visual, text, region and identity evidence as individual passes complete. Schedule harder work based on likely utility, image quality and missed queries. Backfill deferred evidence during suitable device conditions. | Useful retrieval improves as coverage grows. Search stays responsive while work runs. Easily overlooked evidence can still become discoverable. |
| Private personalization | Update aliases, dated reference associations, explicit positive/negative examples and entity prototypes. Experiment with a small calibrator or reranking head if feedback volume supports it. | Feedback improves held-out photos of that subject, avoids collapse on another subject, and can be undone. Confirmed references remain distinct from guesses. |
| Model and policy updates | Compare revised weights, quantization, ranking or scheduling against fixed baselines and a prospective local test. Update affected evidence incrementally and retain a fallback until a replacement is validated. | A real gain survives device, dataset, content and query shifts. Cache/version transitions preserve correctness. Resource cliffs and regressions have explicit rollback criteria. |

Specify which local signals count as evidence. An explicit correction or confirmation is stronger than an opened image, which may reflect curiosity or a bad result. An ignored image says little about its relevance. Use active questions only where the expected gain is meaningful. Describe how to choose high-information suggestions, cap review burden, and avoid reinforcing earlier ranking errors. Do not depend on uploading library photos, personal embeddings, queries, document text or biometric evidence to improve local personalization.

Recommend the smallest learning step that addresses a measured failure. Lay out a progression from no-training changes, to fitting a tiny local ranking or calibration component on limited data, to any proposed offline distillation or fine-tuning. For training, give the expected order of magnitude of labeled examples for each task, minimum useful learning-curve experiment, label sources, split strategy, balancing, negative mining and comparison against frozen alternatives. Explain what to do with sparse labels, incorrect feedback and shifting usage over time. Provide a way to clear personalization and return to the known baseline.

The continuous-improvement design should specify how to learn **what to process**, as well as **what to rank**. A retrieval miss may justify a small, targeted second pass on a shortlist. Explicitly budget the recurrence of such passes. Explain which observations can be reused for future prompts and which should expire after source or model changes. Track the marginal improvement of each additional stage against the extra time, storage and thermal cost.

## 7. Evaluation contract

### 7.1 Build an evaluation that resembles a real library

1. Keep the existing datasets and query lists as frozen regression baselines. Include a shared benchmark manifest with stable IDs, source and licensing terms. Add a realistically mixed library of at least 10,000 distinct real photos. Include ordinary photography, complex scenes, documents, screens and derivatives, small text, repeated contexts and visually similar items. Source appropriate licensed or explicitly permitted cohorts for each modality.
2. Define difficulty strata beyond dataset names. Include low light, small regions, clutter, hard negatives, multiple subjects, edits, missing or misleading dates, multilingual prompts and mixed intents. Label relevant conditions separately so the same benchmark can score category, relation, identity and whole-query correctness.
3. Write prompts from realistic partial memories. Use paraphrase groups and independent annotation. Include exact requests, broad exploratory requests, absent targets, multiple legitimate answers and uncertain content. Use graded relevance and preserve unjudged results. Do not present unevaluated neighbors as negatives.
4. Hold out entities, capture sessions, source groups, form layouts, query templates and near-duplicate families where appropriate. Keep model selection, threshold selection and final testing separate. Show hard-negative results on a genuinely held-out cohort.
5. Evaluate one change at a time before integrating. Cache the same inputs, document decoder differences, expose intentional preprocessing differences, and run paired experiments with uncertainty intervals. Include p95 and slowest actionable cases. Keep candidate and rerank depths visible.

### 7.2 Report outcomes and cost together

| Area | Minimum reporting |
| --- | --- |
| Retrieval | Candidate recall at multiple depths, top 1 and top 5 hit rates, MRR for single-target queries, nDCG for graded relevance, and constraint-by-constraint success. Report macro results by query family alongside overall averages. |
| Identity and grouping | Detection/crop coverage, exact-identity top 1 and top 5, open-set false acceptance, risk/coverage, group merge and split errors, clustering quality, and confirmation burden. Measure both single- and multiple-reference cases. |
| OCR and documents | Text-region recall, character and word error, intended-photo retrieval from remembered text, field and type confusion, false matching of easily confused fields, and success or failure on unreadable cases. Use human text oracle results to estimate the search-only ceiling. |
| Availability | Time until the first useful results, time until 10%, 50% and 95% coverage per modality, p50/p95 warm and cold full-query latency, and coverage during interrupted indexing. Measure results on partially and fully staged galleries. |
| Phone resource use | Weight size, actual persisted bytes per indexed image and region, peak memory, app idle and loading costs, sustained processing throughput, energy or battery impact, thermal behavior, and disk growth during cache migrations. Include device, Android version, model version and execution provider. |
| Robustness | Results by image quality, script, device, subject frequency, scale, and type of hard negative. Compare risk when confidence is high and the target is actually absent. Include fixed baselines and use the same corresponding query sets when comparing models. |

Define at least two physical ARM device tiers and use emulator runs to catch behavioral regressions. Provide a reproducible battery/thermal protocol with sustained runs, foreground and background conditions, and comparable start states. Set concrete acceptance and rollback thresholds before tuning on the held-out set. A decision table should show which improvements warrant added cost and where the current baseline wins.

### 7.3 Bound the first experiments

Recommend an order that can find a wrong assumption quickly. A possible first sequence is to freeze the current routing and ranking outputs, do an error census with oracle inputs, run cheap scoring and candidate-depth ablations on those outputs, and then add one new evidence source for the highest-value residual problem. Follow with a sustained ARM run, a run during staged indexing, and a paired 10,000-image evaluation. Explain where your order differs and why. The goal of early experiments is to choose a design direction with evidence, including the option to stop a promising-looking model after a clear failed test.

## 8. What to return

Produce a decision-ready technical proposal in the following order.

1. **Diagnosis.** State your best explanation for the current failures, supporting and contrary evidence, and what remains unknown. Rank issues by expected impact and how much evidence supports them.
2. **Three design alternatives and your recommendation.** Give a diagram, model and data contracts, indexing schedule, query execution sequence and a concrete resource budget. Name exact checkpoints or published methods only when the evidence supports them. Mark estimates and assumptions.
3. **Pseudocode and a trace.** Show candidate generation, typed evidence fusion, uncertainty handling and selective verification. Trace one generalized compound query across indexed, missing and contradictory evidence, including an absent-target outcome and a fallback.
4. **Entity and on-phone learning design.** Explain detection, grouping, review, reference maintenance, confirmed search, incremental improvement, migration and rollback. Keep exact identity and user-defined ownership decisions grounded in approved evidence.
5. **Experiments and decision gates.** Give an ordered list with dependencies, common manifests and metrics, estimate of data/annotation needs, required devices, approximate costs and stop criteria. State which results would make you change your recommendation.
6. **Build order, risks and stopping points.** Identify the smallest useful production step, independent follow-on steps, and checkpoints for re-evaluating quality and efficiency. For each stage, identify which existing pieces remain useful and how to verify a change without invalidating the baseline.

Aim for a system that can explain why a candidate ranked highly, find more of the right photos as evidence accumulates, and recover from uncertainty or correction. Some requests will exceed what can be observed from the photos and available context. The proposal should define how to surface useful evidence under that uncertainty and how to test that its confidence is earned.
