# Personal names, exact objects, and composed search

18 November 2026. The retrieval design uses the app's confirmed names, cropped visual features and the encrypted local index. It distinguishes a text concept, a specific enrolled entity and a user-declared relationship. Model comparisons and real gallery tests remain separate evidence.

## Decision

Build **category retrieval → reference comparison → evidence-aware ranking**. CLIP can suggest that a photo contains a car. A detector locates the car. An instance encoder compares that crop against examples the user assigned to their car. Only the user can confirm that the car is theirs. Two visually indistinguishable cars may stay ambiguous even with a stronger encoder. If identity is unknown, offer a short review or ask for another reference view.

The existing Android app already provides the right starting point. `NamedLibrary` resolves aliases and `me`, `NamedSearch` intersects user-confirmed photo links, the identity review scans or loads encrypted features, and the ranker selects the best similarity across crop and reference pairs. `IdentityModelFactory` already supports separate face and object encoders. Current face matching uses aligned YuNet and SFace; current object matching uses DINOv2 crop cosine and adds a small hue term when both crops contain sufficient color. Use these as the controlled baseline. See [current workflow](named-photo-entities.md) and [Android identity results](identity-benchmark.md).

None of these studies measures this application's full workload. The practical candidate sequence is the current DINOv2/SFace baseline, DINOv3-small as an exact-object comparator and a specialized ReID model for vehicles. Test additional local verification only if the highest ranked same-category mistakes plausibly share a visible surface. Train or fine-tune after there is a held-out cohort with enough independent identities and sessions. Three examples of one car are useful enrollment data but too little for general model training.

## Execute a query

1. Convert the text to a small plan such as `identity=Self AND identity=MyCar`, `clothingColor=Red`, `around=Surat` and `year=2023`. Recognize only known constraints and keep any unparsed clause for scene ranking. If the user typed `my car` before enrollment, offer to name a car from likely matches. Treat `BMW` alone as a category cue. Treat old and current college as the user's saved chronology rather than inferring life history from image pixels.
2. Return confirmed results from the existing index. Intersect photo IDs for multiple named subjects. Read dates and places when requested from their own evidence. For a spatial or clothing predicate bound to a person, use evidence from the relevant region. A red shirt on a bystander does not satisfy `me wearing red`.
3. Union inexpensive shortlist sources for suggestions. Use cached category vectors, detector hits, confirmed albums and text as appropriate. Keep a detector-miss fallback in Content; a small or occluded car may fail the category gate. Take an offline-measured candidate budget before any query-time decode or new model run.
4. Compare each region with 1–3 confirmed views of the named entity. Compute normalized cosine between vectors from the same model and version. Track the best score, matched view and any strong contradiction. More reference views raise the chance of a high impostor score, so calibrate per enrollment size and category. Save accepted or rejected feedback for the relevant photo and entity. Only an explicit user action promotes a suggestion to a confirmed link.
5. Order results by evidence tier. Show confirmed conjunctions first, then the bounded identity-suggestion tier, then broader partial matches if useful. Within a tier use a measured score or rank fusion. Do not add raw SFace, DINO, CLIP, OCR and distance numbers as though their ranges or probabilities were comparable. For each suggestion, show a short reason such as `resembles your saved front view` or `near Surat and visually similar, car still unverified`.

The ranking itself can use an exact dot-product scan and a bounded top-k heap. One 384-dimensional FLOAT32 vector for each of 10,000 photos is about 14.65 MiB of raw numeric data, with 3.84 million multiply-add terms per reference. Additional regions and durable database overhead change that count. Measure complete warm and cold app paths. Consider approximate nearest neighbors such as HNSW only if a real vector scan becomes the bottleneck, since indexing and checking access can cost much more than the dot products.

## Test the right thing at 10,000 photos

The existing emulator object test uses 96 Objectron gallery frames and 48 queries. It obtained 44/48 top-one hits and 48/48 top-five hits. A cached repeated object query took a median 0.819 seconds. PubFig83 returned 45/48 at both positions and 0.838 seconds for a cached query. The missing face queries failed at reference preparation. Objectron views come from the same tracks. Neither is a real-car benchmark or a 10,000-photo result. See [identity benchmark](identity-benchmark.md).

The held-out COIL-100 subset shows why near-misses matter. DINOv2 with one reference ranked the right toy car first in 22/24 probes, but accepted 38/168 mismatched toy-car comparisons at the broad threshold. Three references increased true acceptance from 16/24 to 24/24 while also increasing mismatched acceptance to 81/168. This is studio toy-car evidence and supports multi-view candidate ranking with separate confidence calibration. See [COIL-100 results](named-photo-entities.md#object-identity-benchmark).

Use two declared measurements.

- **Scale and mixed-gallery relevance.** Read, deduplicate and index 10,000 distinct permitted real photos. Record the exact manifest, captured/received dates where reliably labeled, successful vectors, encrypted index footprint, cold and warm p50/p95, time to first visible results and image decodes per cached query. A mixed public gallery supplies realistic distractors and category coverage. It has no ownership truth.
- **Instance correctness inside that gallery.** Add held-out labeled exact-instance positives and hard same-category negatives. Test Objectron tracks for basic viewpoint retrieval. Use real-vehicle identities and known model labels from authorized VehicleID/VeRi access, or a consented set of same-make/model/color cars photographed across several independent sessions and backgrounds. VehicleID publishes 221,763 images of 26,267 vehicles and provides academic access by agreement. Keep separate partitions by true identity, capture session and camera. Do not treat near-duplicate images as independent or replace hard negatives with unrelated pictures. [VehicleID access](https://pkuml.org/resources/pku-vehicleid.html) · [VeRi access](https://vehiclereid.github.io/VeRi/) · [Objectron](https://github.com/google-research-datasets/Objectron)

Instance-level composed image retrieval is the closest research framing for queries like `my car in snow`. The i-CIR authors provide 202 entities and curated visual, text and combined hard negatives. It is a useful comparison for reference image plus a text modifier. Some entities are product models, characters or landmarks, so it cannot certify physical ownership or matching between two individual units of the same car. Verify exact asset usage terms before selecting or sharing examples. [i-CIR authors](https://vrg.fel.cvut.cz/icir/) · [Google universal embedding evaluation](https://research.google/pubs/towards-universal-image-embeddings-a-large-scale-dataset-and-challenge-for-generic-image-representations/).

Freeze test requests before scoring. Report shortlist recall, judged top-1/top-5, mAP or recall among all observed positives, photo-level false suggestions for absent targets, and open-set miss/false accept rates. Split results by number of confirmed views, same-model lookalikes, occlusion, crop availability and requested text/identity conjunction. Track `confirmed photos`, `suggestions` and `uncertain` independently. Run ablations for full image versus region, one versus multiple views, category gate and geometry verification. Only quote which method wins under the measured conditions. The 10,000-photo and real-vehicle identity runs are proposed here and require actual results before acceptance.

## Executed real same-model vehicle pilot

The small host pilot tested 18 photos of six physical Ferrari 250 GTO chassis. Three visibly reviewed capture sessions per chassis covered different authors or venues where available, front and side angles, repaint, a track fence, and a multiple-car frame. Exact labels come from the linked chassis-specific image collections and file descriptions. Some descriptions explicitly identify the chassis or target region, while generic descriptions rely on the Commons classification. No manual crop used the model scores. [3387GT](https://commons.wikimedia.org/wiki/Category:1962_Ferrari_250_GTO_s/n_3387GT) · [3505GT](https://commons.wikimedia.org/wiki/Category:1962_Ferrari_250_GTO_s/n_3505GT) · [3729GT](https://commons.wikimedia.org/wiki/Category:1962_Ferrari_250_GTO_s/n_3729GT) · [3757GT](https://commons.wikimedia.org/wiki/Category:1962_Ferrari_250_GTO_s/n_3757GT) · [3767GT](https://commons.wikimedia.org/wiki/Category:1962_Ferrari_250_GTO_s/n_3767GT) · [4219GT](https://commons.wikimedia.org/wiki/Category:1963_Ferrari_250_GTO_s/n_4219GT).

Each image became a probe once. It searched six possible chassis, one genuine and five same-model alternatives. Each identity used one rotating reference from a different capture session or the maximum of the other two references. The same crops and sessions fed all models. The CLIP rows compare image vectors. They do not use text queries. DINOv2 used an Android-style central inset square and the existing 85/15 appearance/hue calculation in the hue variant. The benchmark used the app's exact ONNX weight hashes and ONNX Runtime CPU with two threads on Windows. Pillow preprocessing and hand-marked boxes approximate one part of the Android pipeline. No detector or end-to-end Android timing ran.

| Image similarity method | Top 1, one view | Top 1, two views | Top 3, two views | Reciprocal rank, two views |
| --- | ---: | ---: | ---: | ---: |
| CLIP whole photo | 3/18 | 5/18 | 13/18 | 0.538 |
| CLIP manual crop | 6/18 | 8/18 | 13/18 | 0.619 |
| DINOv2 manual crop | 4/18 | 6/18 | 10/18 | 0.517 |
| DINOv2 manual crop with hue | 5/18 | 7/18 | 12/18 | 0.583 |

The same-model pool makes the failure clear. The best tested ranker still put a different chassis first for 10/18 probes. Crop CLIP's two-view median margin over the strongest impostor was −0.0043. Across the sample, adding a second view raised top-one counts for every method, but some individual queries regressed. DINOv2's hue term helped some paint-consistent comparisons and could not resolve repaint and same-color cases. For example, the closed white 3729GT and its earlier red version are the same labeled chassis. A top result for the red probe was another red GTO, 3757GT, under crop CLIP. The ranking is useful for suggestions. It needs a threshold calibrated on more independent identities and an explicit determination of when to abstain. This tiny cohort contains collectible racecars with visually distinct liveries and unequal thumbnail resolution. It does not establish overall superiority or everyday-car accuracy.
