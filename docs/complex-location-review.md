Scope: read-only review of the partial Content location integration, Named parser boundary, location cache, source validation, query publication and visible status. ## Implemented correction reviewed

The original integration checked effective permission before a dispatcher hop. PhotoContentSearch checked location permission through withContext(Dispatchers.IO), and LibraryViewModel subsequently published on Main. PhotoQueryExecution checked cancellation, generation and captured LibraryState, while PhotoSourceObserver delayed invalidation by 350 ms. An effective location or gallery AppOps revocation between the IO check and Main continuation could therefore publish a previously verified location result before state invalidation arrived. Simple Named nearby publication had the same gap. This was a code-path finding, not an independently executed device failure.

Root has now implemented PhotoLocationPublication.current(result, expectedAccess). It checks the current effective location permission and current gallery-access class for NearbyMatches, returning LocationPermission or Unresolved on failure. It is called inside the final publication block for partial Content, simple Named nearby and clothing nearby results. Content discards related rows when the gate changes the result, and retains LOCATION_VERIFICATION unless the accepted result is still NearbyMatches. The direct Named and clothing branches likewise publish no matched rows on gate failure. Ordinary Named matches remain independent of location permission. PhotoLocations.permissionGranted is a synchronous permission check; no per-photo provider scan, database acquisition or location mutex was added to Main publication. Existing background paths handle cache clearing.

PhotoLocationPublicationTest now includes two deterministic regressions: a successful IO result held at a Main continuation is rejected after permission changes, and gallery scope changes reject nearby results while ordinary Named matches remain independent. These exercise injected permission/access suppliers, rather than changing real AppOps. Both executed and passed in the completed verification described below. Revocation during query encoding remains a separate engine concern with final evidence validation. No further severe issue was found in this read-only integration pass.

## Reviewed invariants

- PhotoQueryPlan.kt:62-66 retains the intersection of confirmed non-place entities and a separate saved-place anchor set for partial nearby queries. An empty confirmed intersection remains empty rather than becoming an unrestricted catalog search. Unknown self remains a visible SELF_IDENTITY requirement, so a known object can produce partial suggestions without being presented as confirmation of the person.
- NamedSearch.kt resolves a nearby place only from a complete saved PLACE label suffix. Unsupported entity syntax returns Unresolved for Named. PhotoQueryPlan does not set partialContents or a semantic nearby plan in Named mode; groupPhotoResults returns only confirmed rows there.
- PhotoContentSearch.kt performs GPS filtering before selecting embedding candidates or encoding the query. A location error, missing anchor GPS or denied permission returns no semantic fallback. Partial location queries retain the outstanding LOCATION_VERIFICATION requirement until a NearbyMatches result exists, and groupPhotoResults suppresses related rows while that requirement remains.
- After encoding/ranking, PhotoContentSearch validates one batch containing ranked candidates and all place anchors. Edited/deleted/revoked candidates are filtered; a stale anchor invalidates the result. No new per-candidate gallery read is introduced. Missing source revisions fail closed in this final validation.
- PhotoLocations checks effective location permission, uses revision-bound encrypted coordinate records, checks provider revisions again after reading coordinates and performs a final gallery revision comparison for matched candidates and anchors. Permission denial clears coordinate memory and persistent cache through evidencePermitted.
- Query publication validates the owner coroutine, request generation and complete source/query snapshot. Changing query, mode, names/self selection, source list, folder state or image generation suppresses an old result, provided the effective change has reached LibraryState. The newly implemented immediate permission gate supplements this state-based guard for nearby results.
- LibraryScreen retains the spatial-relation warning when only GPS has been verified. It shows an explicit 30 km radius for both direct Named nearby matches and partial Content location matches. It does not label spatially unverified suggestions as confirmed photos.
