# Entity discovery and fine-detail search

The target is to name a person, object, or other entity once and find its confirmed references from the same search prompt. Users can approve or reject suggestions from a separate review screen. The name belongs to the entity. The encrypted catalog links it to the selected region or a whole-image reference when appropriate.

## Implemented behavior

Name suggestions currently runs face and common-object detection in bounded batches. It shows individual regions. People use aligned face embeddings for candidate ranking. Exact-object review uses region and appearance embeddings and compares them against confirmed references. Unsaved candidates remain outside confirmed-name results. Documents, clothing, places, groups, organizations, and memes can be annotated manually. Automatic unnamed grouping and persistent rejection across review sessions remain open.

## Implementation order

1. Build an unnamed face review from existing region and embedding records. Store cluster proposals separately from confirmed names. Start from mutually similar, usable face crops and check the weakest links against multiple representatives to reduce lookalike chaining. Show a representative crop plus a few examples. Prompt only when there are multiple useful examples. Let users inspect the group, select photos, split or merge proposals, skip, or link to an existing name. A cluster label creates confirmed links only for explicitly selected references. Preserve source revisions and allow undo. Evaluate false merges, missed links, crop failures, and false suggestions for absent people before enabling broad automatic proposals.
2. Keep a separate exact-object workflow. Detect candidate regions, compare objects within compatible categories, and use multiple user-confirmed views. Evaluate a regional encoder and targeted geometric comparison when a shared panel, logo, or sticker is visible. Use same-model and same-color distractors, different viewpoints and backgrounds, and an absent target. Group, clothing and meme retrieval need their own evidence, such as confirmed member intersections, garment regions, and template similarity plus OCR. A model score is a ranking signal. It does not establish ownership or justify a verified confidence percentage.
3. Add local document-type rules or a measured classifier for PAN, Aadhaar, and nearby document types. Require the visible title, layout, and supporting fields together. Treat PAN/Aadhaar mentions in forms or screenshots as hard negatives. Use a confirmed named document or reliable holder evidence for a personal query. Show uncertain documents separately and avoid putting identity numbers in result labels or logs. Use synthetic identifiers and permitted templates for regression tests. [Income Tax Department e-PAN FAQ](https://www.incometax.gov.in/iec/foportal/sites/default/files/2026-01/FAQ%20on%20e-PAN.pdf) · [UIDAI PAN and Aadhaar reference](https://uidai.gov.in/images/news/Link_Aadhaar_with_PAN_using_SMS_02062017.pdf)
4. Add a second ranking pass over a bounded shortlist for visually specific requests. For a dog query, compare general CLIP ranking with real animal region and scene evidence. Freeze negatives such as face filters, drawn dogs, toys, and people with a small background dog. For sunset versus afternoon, use capture time and coordinates to compute locally when reliable, and combine this with sun position or horizon evidence. Treat missing metadata as visual-only and keep warm-colored afternoon pictures and sunrise as hard negatives. [NOAA solar calculator](https://gml.noaa.gov/grad/solcalc/)
5. Report initial shortlist recall, judged rank one and rank five, false confident matches on absent queries, corrections per accepted group, latency, and index cost. Test on distinct people, objects and document templates that were held out from tuning, then qualify phone performance. The existing models are pretrained. Fine-tune only when a frozen, relevant test identifies a gap and a candidate improves it.

## Security boundary

- Local originals stay in authorized Android sources. SQLCipher encrypts the derived OCR, names, regions, and embeddings, with the catalog key wrapped by Android Keystore. Local retrieval uses those records in app memory and works offline. Google ML Kit documents separate SDK diagnostic collection. [Local privacy verification](local-privacy-verification.md) · [ML Kit data disclosure](https://developers.google.com/ml-kit/android-data-disclosure)
- Optional cloud OCR sends only a reviewed full or locally redacted artifact with explicit approval, bound to its mode, digest, source revision, and destination. The worker can read the approved copy for inference. Revision and access checks govern local integration. Avoid sending identity embeddings, named groups, private annotations, or ordinary search prompts as part of the entity workflow. [Hybrid design](hybrid-implementation.md)
- Keep proposed links separate from confirmed data. Recheck access and source revision before preview, confirmation, reuse, or applying a late result. Delete or invalidate derived records when access or source revisions change under the existing lifecycle policy. An app-level credential lock and explicit lost-key rebuild remain release work.
