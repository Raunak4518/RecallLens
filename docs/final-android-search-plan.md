# Final product and engineering plan — standalone Android photo search

**Product decision.** Build a private Android app that searches the photos already accessible on the phone. The user gives it one prompt. The app finds scenes, visible words, documents, people, individual possessions, events and combinations of these. It indexes each photo progressively and learns local names through review. Gallery access, inference, personalization, retrieval and result display all work offline. The Android product owns its release, models, keys and index. It has no service account, upload queue, remote inference fallback or dependency on a second product.

**Architecture decision.** Use a small image–text encoder for broad recall. Give text, personal entities, dates, places and selected image regions independent ways to retrieve a photo. On a shortlist, check whether the requested evidence belongs to the **same subject, at the same time, in the same photo**. Store reusable observations. Run another model only when it can recover a missing candidate, distinguish close candidates, or enrich a useful part of the library in the background.

**Status of this document.** This is the target design and build order. The existing benchmark measurements are identified below. New thresholds, hardware budgets and model choices are proposed controls for experiments. The winning models will be selected on held-out photo searches and physical Android measurements.

## 2. How the working app behaves

1. The user grants gallery access. Accessible files enter a local inventory. Only photos with usable indexed evidence appear in the searchable collection. Show the unique processed count and make partial text or entity coverage clear when it affects a search.
2. The user can search immediately after the first batch. Cache reads and lightweight query work take priority over further background inference. A repeat search should normally decode zero originals. Opening a result can load the original from its current permitted URI.
3. A separate review section shows model-selected **regions** and representative crops for anonymous groups. Naming a region creates a personal subject. The app looks for other sightings and asks for confirmation. A photo may contain several subjects, and a subject may appear in many photos.
4. One search field handles broad and personal requests. Results with well-supported conditions appear first. Additional relevant but uncertain candidates may follow. Explicit Named results require confirmation for the named entity. A confirmed person with an estimated attribute retains both pieces of provenance.
5. The search can return no supported match. When detail processing is pending, explain what evidence is still becoming available. When the photo lacks a distinguishing detail, offer inspectable alternatives. An ordinary query never triggers a synchronous gallery-wide scan.
6. After edits, moves, deletion, trash, permission changes or restart, the app refreshes only affected evidence. Undoing a name or correction reverses its personal associations. The user can erase local learning and rebuild derived data without modifying original photos.

## 3. Components and ownership

Keep Kotlin and Compose, Android media access, WorkManager, Keystore and encrypted persistence as the starting implementation. Separate responsibilities by change boundary. Five internal packages and an evaluation harness are sufficient initially. Use an interface when there are competing implementations or an I/O boundary.

| Component | Owns | Output or contract |
| --- | --- | --- |
| Library | MediaStore access, stable references, revisions, orientation, deletion and permission checks | A stream of accessible source revisions and a bounded way to decode a requested size or region |
| Analysis | Durable stage scheduling, model registry, inference sessions, memory and time budgets | An extractor accepts a revision and pixel region. It returns typed observations, model/preprocessor version, source geometry, quality and stage outcome. |
| Index | SQLCipher records, lexical postings, time/place lookups, vectors and transactional checkpoints | Retrieve by an evidence type and revision, publish completed batches atomically, invalidate affected evidence |
| People and things | Region detections, anonymous groups, confirmed references, aliases and history | Resolve a name, retrieve confirmed sightings, propose unconfirmed sightings and apply reversible feedback |
| Search | Prompt interpretation, candidate union, evidence binding, verification, ranking and coverage | Each result carries source revision, matched clauses, unresolved clauses and reasons. The screen consumes one result stream. |
| Evaluation | Versioned fixtures, recorded candidates, labels, model outputs, stage timing and resource traces | Replay a change without rereading private photos or rerunning every model. Test inference, candidate generation and rank changes independently. |

Persist source revision, normalized box and producer version on every observation. A garment record points to the person region it describes. A document field points to its value and supporting label spans. Store confirmed associations independently of model vectors. Record stage states individually: pending, usable, completed without usable evidence, temporarily failed and unsupported. A missing detection is weak evidence of absence.

**Standalone build boundary.** Remove remote-processing screens, job configuration, network workers and endpoints from the Android product composition and packaged manifest. Use bundled models for the baseline so first launch works in airplane mode. For optional model packs, allow an explicitly installed, integrity-checked local pack and show which capabilities are available. Migrate existing installs with fixture copies of each supported database version. Preserve confirmed names and valid local records. Preserve previously imported results with their original provenance pending a local recomputation or user removal. Never relabel inherited OCR as locally produced. Cancel obsolete pending job execution and discard obsolete credentials under a versioned migration. Verify package contents and offline first-launch behavior before releasing the change.

During foreground search yield background work between images, bound bitmap memory, and cancel obsolete queries using a generation ID. Resume using a committed cursor and recheck source revision before every write. ## 5. Model choices by task

The shipping baseline and first challengers are deliberately different columns. “Best” means the largest reproducible gain on that task within the device envelope. A replacement that improves broad scene recall can still be a bad identity or document model.

| Task | Starting implementation | First challengers and promotion test |
| --- | --- | --- |
| Broad scene and multilingual image retrieval | Quantized CLIP ViT-B/32. Cache the text encoder and search global image vectors. | Compare MobileCLIP2-S0 and S2 against the identical baseline on ordinary, compositional and rare queries. Use SigLIP 2 Base as a quality comparator. Benchmark both towers, quantization, preprocessing, sustained ARM speed and total installation. Apple's published mobile results use Apple hardware and its weights have separate research-model terms. Only distribute a checkpoint whose actual terms permit the intended use. [MobileCLIP2](https://github.com/apple-aiml-research/ml-mobileclip), [SigLIP 2](https://huggingface.co/google/siglip2-base-patch16-224) |

Compare ML Kit's script-specific paths for the scripts actually supported. Test English, Hindi, mixed-script and out-of-support inputs explicitly, including Gujarati if it is a product requirement. Choose per-script defaults only after device tests. Measure CER, intended-photo hits, false exact-field matches and time. [PaddleOCR model families](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/algorithm/PP-OCRv6/PP-OCRv6.en.md), [ML Kit script coverage](https://developers.google.com/ml-kit/vision/text-recognition/v2) |
| Document type, layout and exact fields | OCR spans plus a small field schema and layout rules. A class/holder contradiction disqualifies an exact-document claim. |
| Person discovery and identity | YuNet detections, SFace alignment/embedding, quality gates and reference lookup. | First isolate detection and alignment with human boxes. Compare multiple exemplars against one. Evaluate a quality-aware face encoder such as AdaFace offline as a teacher/upper-bound candidate, then trial a compact student only if it fixes the same real errors. Record exact weight origin and rights. Measure open-set false accepts at realistic gallery size. [AdaFace](https://github.com/mk-minchul/AdaFace) |
| Object category and exact instance | YOLOX-Nano for boxes. On rigid textured items compare a cheap local-keypoint geometry check on the top few candidates. Common logos and repeated patterns require impostor controls. Never infer ownership from appearance. [DINOv2](https://github.com/facebookresearch/dinov2) |
| Attribute and relation binding | Person boxes and existing garment masks. Compute color over the visible garment pixels under plausible illumination. | Compare conservative ownership to neighbor-excluding masks. Train a compact region-pair verifier on subject assignment, relative position and common actions only if geometric rules lose on held-out scenes. Record which relations have reliable evidence. Occlusion and apparent depth may stay unresolved. |
| Depiction, scene state and fine detail | Global and crop embeddings plus metadata with source and precision. | Fit small independent heads on frozen features for real scene vs portrayal, filter/overlay, screenshot and visually meaningful states. | Query language and paraphrase | Local alias dictionary, token normalization, literal spans, calendar parsing and typed clauses. Keep a whole-prompt semantic route. | For unseen wording, compare a small local text model for intent/slot extraction with a compact grammar and alias baseline. Keep personal names, quoted strings and IDs exact. Test multilingual clause resolution separately from multilingual OCR and image-text alignment. Small visual or language models must pass airplane-mode and memory tests. |

For each comparison record checkpoint, conversion hash, preprocessing, tokenizer, quantization scheme, supported operators, CPU fallback and deployment rights. Compare float output on a small fixture before judging INT8. Measure peak memory while image and text sessions overlap under the actual runtime. The prior SmolVLM2 pilot took about 24 seconds per warm image on the emulator. Include a controlled generative challenger on difficult images, with cached claims linked to regions and explicit hallucination scoring. Admission to the interactive path requires a physical-device latency win within budget. [ONNX Runtime mobile deployment](https://onnxruntime.ai/docs/tutorials/mobile/)

### 5.1 Find exactly where entity identification failed

Keep the identity pipeline inspectable at eight points. A high final similarity score cannot recover a missed region or identify a physically indistinguishable item.

| ID | Smallest decision to improve | Test and optimization |
| --- | --- | --- |
| E1 | Did we propose the right pixels? | Measure region recall by size, border location, clutter, occlusion and subject type. Compare detected boxes, a small set of overlapping tiles, and class-agnostic proposals on photos with poor known-category coverage. Hold retained vector count constant. |
| E2 | Did preprocessing preserve the identifying detail? | Use human crops as an oracle. Compare alignment, context padding, masked foreground, aspect-preserving fit and native-resolution detail crops. Cache coordinates in oriented source space. Revalidate after rotation or edits. |
| E3 | Did the correct instance have a chance? | Compare full photo, best crop, pooled parts, one reference and several independent-session exemplars. Label candidate misses separately from verifier rejections. For crowded photos calibrate over region count: selecting the maximum from many regions creates more false-match opportunities. |
| E4 | Does another instance explain the image equally well? | Compare the best exemplar with the strongest competing confirmed identity and visually close unknowns. Check texture/geometry on rigid items with repeatable local details. Treat identical designs with no visible distinguishing marks as unresolved. |
| E5 | Is this relationship physically consistent? | Construct a small region assignment for each shortlisted photo. Two distinct named people require two distinct face regions. Bind clothing to the correct person box/mask. Compare ownership with an oracle and score swapped roles, occlusion and overlapping subjects. |
| E6 | Is the group safe to name? | Penalize burst duplicates as independent evidence. Keep explicit cannot-link decisions for confirmed mismatches. Check mutually similar representatives across captures before proposing a merge. Simulate the impact of one wrong seed and measure affected photos, review taps and undo coverage. |
| E7 | Did we preserve the user's intended type of identity? | A document class differs from a particular edition; a recurring place differs from a photo taken nearby; a meme template differs from its text variant. Encode the type before linking. Grade exact unit, version, group and category relevance separately. |
| E8 | Does a learned improvement transfer? | For every proposed feature record additional verified instances recovered per MiB, per 1,000 photos processed and per second of review. Split by unseen identity and capture session. Run detector→linker→retriever through the app as well as isolated oracle experiments. |


## 6. One prompt from input to results

**Plan the request.** Split into clauses, each with subject, property/relation, polarity, required or preferred status, original source span and uncertainty. Keep whole-query visual search as a fallback when parsing is incomplete. For a genuine ambiguity preserve at most two plausible structured interpretations initially. Treat a personal alias as a candidate entity with an effective date. Interpret exact identifiers and quoted text through a literal branch. Distinguish an observed event appearance, a calendar occurrence and actual attendance.

**Retrieve candidates independently.** Start tuning with top 100 each from global visual similarity, text/document postings and relevant region/instance similarity. Also retrieve all currently accessible confirmed members of a named entity and exact structured matches through paginated postings. Search capture-time intervals and proximity to known place anchors as additional candidate paths. Reserve space per route before a bounded shortlist. Candidates can enter solely through a recognized word or face even when the global scene score is poor. Compare recall at depths 25, 100 and 300 before setting production caps.

**Bind and rank.** Evaluate each required clause as supported, contradicted, unresolved or pending. Check subject IDs and evidence regions for conjunctions. Withhold exact status if an important clause is unresolved or a reliable value contradicts it. Rank complete matches first, then useful partial matches. Use a calibrated support floor for open-set searches. Within a tier start with reciprocal rank fusion using at most one contribution from correlated views of the same evidence. Train a small pairwise ranker only if it improves over that transparent baseline. Return all supported matches through pagination, followed by up to five related candidates above an independently calibrated floor. Keep speculative identities out of Named results.

**Verify selectively.** For each top candidate estimate how far a requested unresolved clause could move it and the time needed to check. Prefer the smallest useful verifier: a stored region join, then a cached crop vector, then original-pixel inference. Return the cached answer before the deadline. Enqueue further work if it could change a meaningful result. Use the same query and source revision when publishing later improvements. Measure first-result quality and time to stable top five. A reranker cannot recover candidates that never entered its pool. For low candidate recall, change the retrieval route or collect missing evidence across the library.

**Three acceptance traces**

- **A named subject with an attribute and place.** Resolve the confirmed subject, find its appearances and look up a place anchor. Associate the attribute with the correct region inside each photo. A matching outfit on another person cannot satisfy the clause. Rank nearby photos with suitable distance evidence. Missing GPS can yield a visually plausible related result, with location unresolved.
- **A remembered document among similar forms.** Search heading alternatives, layout and class to retrieve documents. Link the requested value to its role. Exact ID evidence overrides generic form appearance. A form with the wrong holder or edition cannot become a full match through shared boilerplate. If OCR has not reached the relevant photos, record the pending text pass and prioritize likely documents.
- **An event or visual condition.** Look up supported event windows in a versioned offline calendar with region/year. Search visual event evidence independently and combine it with capture date, inferred episode and import-time provenance. A delayed import can still rank highly. An afternoon timestamp alone cannot prove afternoon lighting, and common decorations alone cannot prove attendance. Maintain separate confidence for each claim.

### 6.1 Rewrite the query without changing what the user asked

Treat rewriting as an optional retrieval experiment. Keep the original query and its ranking trace. A rewrite earns its place when it recovers relevant photos for a paraphrase, typo, script or ambiguity the baseline missed. Track which precise rewrite introduced each candidate and whether a later verifier supported it.

| Step | Operation on the phone | Contract and targeted test |
| --- | --- | --- |
| Q1. Read once | Capture raw spans, language/script hints, local time zone, search scope and index generation. Normalize a second copy for lookup. Preserve the original characters for exact fields. | Full-width digits, leading zeros, hyphens, punctuation and case can matter. Test exact field equality with documented per-field normalization. |
| Q2. Protect meaning | Mark names, quotes, dates, quantities, units and identifiers. Build a small clause tree for AND, OR, negation, ownership and roles. Keep explicit hardness and source spans. | A swap in who wears a color must change the plan. An OR must not silently become an AND. Preserve the scope of a negative within a clause. |
| Q3. Resolve private references | Map a confirmed alias or self reference to local entity IDs with effective dates. Resolve relative times at query time. Keep ambiguous aliases as alternatives. | Compare a person sharing a place name, an old organization, “last year” across New Year, and alternate spellings in mixed script. |
| Q4. Form bounded variants | Start with the raw semantic route plus at most two expansions. Try curated synonyms, spelling variants, transliterations and document vocabulary by type. Use weighted synonyms or alternate clauses internally so the original literal remains searchable. | A transliterated name may resolve an alias. A spelling rule must preserve literal document numbers. Track rewrite-only relevant hits and wrongful promotions independently. |
| Q5. Plan per route | Use short natural phrases for the visual encoder, positional terms for OCR, exact bindings for named entities, and intervals or proximity for metadata. Split a long prompt at clause boundaries before it reaches the encoder's token limit. | Check all required clauses survive truncation and preserve identity and relationship direction. Escape user text in full-text syntax and pass parameters to database queries. |
| Q6. Escalate ambiguity selectively | When two readings survive, retrieve cheaply for both. If their top results diverge materially and the interpretation changes a required condition, offer one short clarification after the initial results. | Benchmark the raw prompt, deterministic rewrites, and a small offline learned planner under the same candidate/time budget. Only run a learned rewrite when its incremental benefit justifies startup and inference. |

**Worked rewrite.** “Me in red near my old college” becomes a confirmed self ID, a garment-color predicate bound to that same person's region, and a soft distance predicate around a dated institution anchor. The visual route may encode a person wearing red. The named route retrieves confirmed self sightings. The location route retrieves candidates around the relevant anchor. The word “old” qualifies the history of the institution relationship. It does not describe the age of the building. Retain ambiguity if multiple earlier campuses qualify. “Red near me” must produce a different relation graph.

**Replay tests.** Use paraphrase sets that should yield equivalent results and minimal pairs that should differ. Change exactly one owner, polarity, conjunction, edition, date, value, literal or direction. Report protected-span corruption count, intent/slot accuracy, relation-edge accuracy, contrast-pair discrimination, candidate recall changes, net gained/lost top-five hits, added milliseconds and energy per rewrite. A new rule fails release if it changes a protected identifier or explicit polarity on the invariant suite. Prefer the raw route when an expansion adds latency and unhelpful candidates.

### 6.2 Decide how to execute the plan

| Subproblem | First implementation and challenger | What decides |
| --- | --- | --- |
| Text index | Store positional OCR postings and tagged fields in encrypted storage. Maintain a separate exact identifier lookup. | Compare fixed transcripts using intended-photo recall, short-string collisions, indexed bytes and write cost. **Bound optional work.** For a candidate verifier estimate its chance of changing the visible answer, expected relevance gain and measured device cost. Run the highest expected gain per millisecond that fits the remaining deadline. Start with rules for unresolved required clauses and close competitors. Compare that policy with verifying none, the top five, and every candidate in a fixed small pool. Publish initial evidence immediately. If the winning photo usually falls outside that pool, invest in retrieval or enrichment instead of tuning this policy.


## 7. Local learning that improves the next search

**Discover groups.** Start from high-quality automatically detected regions. Link mutual nearest neighbors only above a type-specific threshold and a margin over the closest competing identity. Check group consistency against representative members before extending it. Avoid transitive merges through a single ambiguous region. Choose representative crops from different sessions and viewpoints. Apply per-type identity rules: a face identity, a document version, a physical object, a group of named people and a media template need different definitions of sameness.

**Name once and review new sightings.** A typed label attaches to an entity ID and specified regions. Store diverse confirmed exemplars and explicit rejections. Start with one to four exemplars. Search new regions against prototypes and hard negatives. Favor review examples that resolve confusion or add a new viewpoint. Keep accepted links distinct from predicted links. Reject, split, merge, remove and undo operations recompute only affected personal references. “Me” requires explicit self selection. Dated personal relationships such as attendance at an institution are user-provided context with effective dates.

**Improve without training on private galleries by default.** An explicit correction changes the local reference set immediately. Opening a result or scrolling past it has ambiguous meaning. On licensed development data, start with frozen encoders and train a small ranker or routing head on 100, 300 and 1,000 labeled intents as a learning curve. For hard relations, prototype on 1,000–10,000 region pairs from disjoint scenes and measure whether more labels still help. Distill from a stronger offline development model only where it beats the existing method on the residual task. Human adjudication stays independent of the teacher. On-device personalization should work from the first confirmed example and should be reversible without retraining an encoder.

### 7.1 A tiny feedback control with immediate value

Every result has an accessible **Wrong result** action in its existing menu, with a minimum accessible touch target. One tap removes the item from this result set and offers **Undo**. No modal rating is required. Optionally offer **Why?** with a few relevant choices derived from the query, such as wrong subject, detail, text, place/time, or duplicate. Allow “unsure.” For a region-specific correction, outline the exact region and ask the user to identify the erroneous association. Keep **Found it** and **Choose the photo I meant** optional. The latter can identify a missed processed photo outside the shortlist.

| User action | Immediate effect | Eligible learning signal after opt-in |
| --- | --- | --- |
| Wrong result | Suppress this photo for this query/session, restore on Undo. Other searches can still find it. Offer an explicit “remember for this search” choice for durable corrections. | A weak negative for the exact intent–photo pair. The event says nothing by itself about the identity, color, date or text in the photo. |
| Wrong person or object, region explicitly selected | Reject that proposed entity–region link. If a previous user-confirmed link is involved, offer to edit that specific saved association. | Negative exemplar for that entity at that source revision. One rejection must not propagate to everyone in a group. |
| Wrong detail, field, place or event | Record the disputed clause in context. If the user supplies a factual replacement, show the changed value and its scope before saving. | Clause-level negative, or a corrected typed observation with user provenance. Keep the original extractor output available for evaluation. |
| Duplicate or wrong version | Hide that derivative in the current broad result family. Exact-version queries can still retrieve it. | Diversity or version preference bounded by intent. |
| Found it or choose intended photo | Surface the selected photo and record whether it came from the candidate list, a lower page or outside the pool. | Explicit positive. With an explicit negative for the same intent it creates a supported preference pair. A missing intended photo is evidence about retrieval coverage. |
| No action, tap to inspect, short dwell or back | Ordinary browsing. | No relevance label. A user often opens a poor result precisely to inspect it. |

**Permission boundary.** Off by default. Offer a distinct setting, **Learn from my corrections on this phone**, with short copy explaining the data, effect, retention and undo/reset. With it off, one-tap dismissal is session-only. Deliberately saved names and corrections remain normal user-managed records. Granting permission starts a new consent epoch for subsequent explicit feedback. Include an independent choice before reusing older saved corrections for training. Turning learning off immediately serves the baseline ranker, cancels pending training, and clears training-only events, derived models and training checkpoints. User-saved names or rules remain individually editable. Revoking gallery access removes affected photos from search immediately; dependent training material must be invalidated and rebuilt or purged.

### 7.2 Train the smallest model that can use the evidence

1. **Capture minimally.** In encrypted local storage record feedback ID, canonical intent fingerprint, source/region revision, judgment, optional clause ID, consent epoch, model/feature versions and event time. Store only the necessary score/feature vector for replay. Record exposure and rank only for submitted examples, with permission. Avoid storing pixels or raw prompts for training by default. Show the user their saved corrections in a deletable history. Proposed starting limits are 90 days and 2,000 training-only events, whichever is reached first. Prune learned influence when events expire.
2. **One correction already works.** Apply exact-intent suppressions and factual link corrections immediately. Generalizing a single ambiguous thumbs-down across an entity or an entire category is too broad. With sparse feedback use fixed fusion and explicit references. Surface few, diverse review questions when an answer resolves a real ambiguity.
3. **Use a small personal reranker.** Freeze image/text encoders. Start with a regularized linear residual over a compact set of features such as normalized lexical strength, visual margin, supported-clause fraction, binding quality, identity margin, temporal agreement, depiction type and missing-stage flags. Add a bounded residual to the baseline score **within** the existing eligibility tier. Strong contradictions, access gates and confirmed-only membership remain outside the model. A generic negative alone can support scoped suppression. Fit pairwise logistic loss only from a same-intent explicit positive and negative. Weight repeated judgments of the same photo/session once. Reversing a judgment supersedes its previous event.
4. **Define when fitting is worthwhile.** As an experimental trigger, attempt a shadow fit after 30 usable pairs spanning at least 10 distinct intents and several sessions; tune on development simulations. Time-ordered future evidence determines promotion. If the holdout is too small or contains one repeated subject, keep collecting consented judgments and serve fixed fusion. Treat these counts as a trigger to test, never proof of generalization. Compare exact corrections only, exemplar updates, a scalar per-route calibration and the residual model. The simplest winning variant ships.
5. **Keep training cheap.** Train on cached feature vectors during idle/charging windows. Start with at most 3 epochs and a 5-second job budget; checkpoint or abort on resource pressure. Optimize on-device only over the small weight vector. Measure training CPU, peak RAM, disk and energy before allowing more. A simple Kotlin numerical implementation is viable for this small linear head. Larger heads need a separately benchmarked runtime/weight-update and persistence path.
6. **Test future utility.** Score later sessions and previously unseen photos of known subjects; hold out near-duplicate families. Compare with fixed fusion with identical direct corrections. Keep a protected set of unrelated queries and absent targets. Report wrong-result recurrence, correct top-one rate, pairwise preference wins, nDCG@5, candidate recall and false confident identities. Wrong-only feedback samples displayed mistakes; it cannot establish unbiased library-wide improvement. Use independent judged fixtures for general claims. Clicks, unseen photos and gallery order do not manufacture negatives. [Primary research on exposure bias in learning to rank](https://arxiv.org/abs/1608.04468)
7. **Promote reversibly.** Fit under a new version in shadow mode. Proposed gate: positive held-out improvement over direct corrections alone, unchanged Named/access invariants, no priority-slice regression beyond the Section 9 margin, and resource budgets met. If uncertain, continue with the fixed model. Record the active base model, feature schema, event set and consent epoch. On undo, revoke, deletion, expiry, re-label or incompatible feature migration, immediately disable the affected residual; recompute from remaining eligible events and switch atomically after validation. Interrupt/restart at each step and check that revoked influence cannot return through a cached result or old checkpoint.

**Concrete distinction.** If the user rejects a face-filter photo in a search for a dog, the first tap only suppresses that result for this intent. A reason such as “filter/depiction” supplies evidence about literal-animal requests. The same photo can still be a good result for a search for face filters. If instead the app retrieved the correct dog but the wrong location, a place-specific correction should affect the location evidence. The control must allow either interpretation.


## 8. Phone resource budget and operations

| Area | Proposed target and decision rule |
| --- | --- |
| Interactive response | Warm end-to-end p95 ≤3 s at 10k real photos during idle search **and** active indexing. Measure first usable result and stable top five. Suggested envelope: 0.3 s planning/encoding, 0.5 s retrieval, 0.5 s evidence evaluation, 0.4 s delivery and first thumbnails, 1.3 s headroom. Bound optional verification by the remaining time. |
| Derived disk | Initial design ceiling of 100 MiB at 10k and 500 MiB at 50k, with weights and transient migration space reported separately. Project the measured scene store at 4,695 B/photo. Add 0.8 retained detail vectors/photo × 640 B plus 3,072 B/photo on average for OCR, metadata and postings, with 25% overhead on increments. Estimated totals are about 87.5, 218.7 and 437.5 MiB at 10k, 25k and 50k. Measure actual SQLCipher pages, WAL, heavy-text outliers and post-compaction size. |
| RAM and thermals | Profile one lower-memory ARM device and one faster device. Run sustained indexing for ≥30 minutes with the screen condition, battery band and thermal starting state recorded. Measure peak PSS, model opens, decoded bitmap size, time in thermal throttling and battery drain per 1,000 photos. Admit overlap only if foreground p95 stays within target and sustained output improves. |
| Model packages | Ship the smallest measured winning combination for essential offline search. Use separate, versioned local packs for rare scripts or costly specialists when justified. Verify packaged bytes, installed bytes, startup memory and first-use behavior. On low free space retain confirmed records and compact or evict recomputable detail features first. |
| Cache, privacy and upgrades | Use app-private encrypted storage for embeddings, spans, boxes, names and personal links. Keep key material protected by Android Keystore. Enforce source permission at read and publication. Keep private features and queries out of analytics, crash attachments and backups that would break the local-only contract. Stage new feature spaces, validate them, switch atomically and retain a rollback plan. Measure peak disk during the transition. |

### 8.1 Profile the full critical path

Instrument accessibility/permission checks, MediaStore enumeration, queue waiting, source opening, decode/rotate, bitmap transfers, session open, per-model inference, postprocessing, encrypted read/write/commit, query parsing and encoding, postings/vector scan, evidence joins, ranker, first thumbnail and stable top five. Use monotonic timestamps, an operation ID and stage counters on permitted benchmark fixtures. Record stage overlap and critical-path elapsed time rather than summing concurrent durations. Include model cold start, OS page-cache behavior, allocations/GC, queued pixels, canceled work and contention with the UI. Production diagnostics can use aggregate durations and counts. [Android Macrobenchmark](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-overview)

| Processing target | Concrete comparison | Correctness or cost check |
| --- | --- | --- |
| Library discovery | Full enumeration versus paged incremental changes with periodic reconciliation. Skip verified-current revisions. Compare batched access validation to one resolver operation per item. | Use fixture sequences of add, edit, move, trash, restore, revoke and interrupted reconciliation. Immediate access recheck on display. Count source opens, rereads and useful commits. |
| Decode and model inputs | Decode at the actual required size, reuse orientation transforms and limit live buffers. Benchmark lazy crop decode from source versus repeated full decode. Test reuse of a single decode across compatible models. | Compare pixels/boxes after rotation, extreme aspect ratios and small detail. A reused thumbnail can drop OCR characters; measure retrieval alongside saved time. |
| Model execution | Reuse sessions within time slices. Sweep batch size, number of CPU threads, quantization and available delegates one variable at a time. Include native startup, copies, fallbacks, RAM and throttled speed. | Measure sustained useful outputs/minute per modality. Compare accepted results with float/CPU controls and report disagreement near decision thresholds. |
| Database and checkpoint | Buffered transaction size, prepared statements, batched evidence fetches, avoiding N+1 thumbnail/region reads, indexes aligned to frequent joins, compact vector layout. Measure WAL growth and checkpoint timing. | Inject interruption after decode, inference, write and cursor advance. Require durable progress, identical results for lossless variants, bounded replay and current permission checks. |
| Work scheduling | Compare baseline, time slicing, aging deferred work, deadline-aware priorities and bounded background overlap. Cancel outdated stages before loading a model. | Measure age of oldest job, time to 10/50/95% ready by modality, searches while indexing, wasted CPU after cancellation, and useful completed unique photos per hour. |
| Data reduction | Evaluate vector FP16/INT8, lower-dimensional learned projection, region caps, optional rerank on original precision, and exact/near-duplicate reuse. Copy derived evidence only for verified identical pixel inputs under compatible models; keep source metadata and access independent. | Measure encrypted bytes, recall degradation, false merges and full-query time. Count original-pixel reads per repeated search. Fit learned projections only on development data. |
| Display | Batch thumbnail loading for visible rows, bounded memory cache by source revision and size, scrolling cancellation, background verification updates with stable ordering. | Measure actual first relevant thumbnail, time to stable results, frame jank, wasted thumbnail decodes and accessibility target usability. Keep timing independent of debug text logging. |
| Device adaptation | Learn a per-device cost table for stages from aggregate local timings. Prefer conservative defaults until enough observations exist. Downshift concurrency when foreground, thermal or memory conditions change. | Compare against a fixed policy over identical sustained runs. Assess fairness to document and entity queues. Report energy measurements with method and uncertainty; use long-run battery change where fine counters are unavailable. |

**Benchmark protocol.** Use at least 200 warm query observations per device and condition as a starting point for p95, spread across at least three alternating-order runs. Separate cold app, cold model, warm unique prompts and repeated prompts. Exercise burst typing, canceled queries, foreground queries during indexing, photo edits and feedback invalidation. Record latency distributions together with initial relevance, stable relevance and bytes moved. Exact-scan controls become particularly important for approximate search over filtered sets. Accept a lossless optimization only after returned IDs and stable tie order match the reference. For approximations, publish the recovered compute alongside every lost query family. Escalate complexity only when a trace identifies the expensive stage.


## 9. What proves a change is better

Freeze the current app, a permitted 10,000-distinct-image gallery and a manifest of hard cohorts before replacing components. Build an independent mixed test set covering text-bearing photos, real documents, same-design items, groups, events, tiny edge details, low light, edited media and screen depictions. Hold out identities, source sessions, form templates, near-duplicate families and paraphrase groups. Label fully relevant, partially relevant, wrong and unjudgeable. Include absent targets. Keep existing public cohort results as historical regression controls. [Project evaluation brief](astra-on-device-photo-search-model-brief.md)

| Failure question | Experiment | Proposed promotion gate |
| --- | --- | --- |
| Can the correct photo be retrieved at all? | Compare routes alone and in union. Inject the correct parse, crop, transcript or candidate separately. Measure recall@100 and identify the first failure stage. | Target ≥95% intended-target appearance at candidate depth 100 on judgeable single-target queries. Publish per-family results. Widen/deepen retrieval before investing in a reranker if this gate fails. |
| Is the whole prompt answered? | Compare baseline, fusion, region binding and selective verification on the same candidates. Use swapped roles, wrong field values, same-category impostors, absent targets and misleading dates. | Aim for ≥0.05 absolute mixed-query nDCG@5 improvement over the current system, with a paired 95% interval above zero. Report top 1/top 5 and full-clause success. Investigate every priority family down >2 percentage points. |
| Is an identity suggestion safe and useful? | Measure detection coverage, false merges/splits, cross-session hits and false strong matches. Use independent absent-identity searches separately for people and possessions. | Confirmed-only invariant in every test. Proposed suggestion floor ≥95% precision at ≥30% coverage of matchable queries. For a <1% upper 95% false-strong-accept bound, roughly 300 independent absent trials with zero errors are needed per claimed cohort. Retain review when evidence is insufficient. |
| Is OCR better for users? | Pair engine results for remembered-text retrieval and document-field accuracy. Report gained and lost queries plus recognition errors and cost by script/readability. Compare against human text and human crop oracles. | Require a positive paired gain on held-out intended-photo retrieval and no material increase in wrong exact-field matches. Fit fallback triggers on development data only. |
| Does it work on the device? | Run the normal gallery-to-search workflow on both physical tiers, cold, warm and during indexing. Test edit, deletion, access revocation, reboot, cancelled search, interrupted migration and airplane-mode fresh launch. | Meet latency and storage budgets. Zero exposed inaccessible/stale results, speculative Named links or required network calls. Repeat each condition at least three times and report variance. |

**Evaluation cost and discipline.** Begin with 200 sampled failures/successes. For the larger set, 600 independent intents × 15 pooled candidate judgments × 20 s is roughly 50 reviewer-hours for one annotation pass, before writing prompts and adjudication. Use that as a planning estimate. Preserve unjudged neighbors. Track annotation disagreement, hard-negative selection and test contamination. Report 95% uncertainty by independent query or entity. Increase samples when the uncertainty is too large to support a release claim.
