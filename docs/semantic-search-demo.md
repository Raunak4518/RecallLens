# Semantic search for the Android demo

The demo prioritizes local search that returns from the encrypted index within seconds. Separately approved cloud assistance stays outside the demo path. The app uses its image/text encoder for appearance search, OCR for words in images, and confirmed names for the people and objects a user has labeled. Capture years and existing saved-place GPS evidence narrow eligible photos before ranking. Appearance estimates remain separate from confirmed identity.

Open an indexed photo and choose **Find similar photos**. The app ranks existing gallery image vectors against that photo's vector. It skips the original photo in the results and requires no text or image encoding during the search. The user can open a result or return to text search. The photo must have completed visual indexing.

Use **Photo contents** or **Named** with a trailing `in 2023`, `before 2023` or `after 2023` to use the Android gallery's recorded capture date. Missing capture dates are omitted from dated results. File modification dates cannot establish a capture year. Exact text and filename mode keeps its literal query.

## Measured model decisions

The Android CLIP baseline ranked 2,000 real photos for 24 frozen requests. Two reviewers visually judged the 192 top-eight candidate slots with scores and ranks hidden. The 20 ordinary requests returned a relevant top result 10 times and at least one relevant top-five result 16 times. Three top results and 17 top-five slots were unjudgeable. This is a provisional fixed-pool comparison based on AI review. The encrypted scene index occupied 10,260,541 bytes and reopened in 1.753 seconds with zero image decodes. See [pilot protocol](relation-vlm-pilot.md).

SmolVLM2 500M Q8 ran on the x86_64 Android emulator. Shrinking the first input reduced a fresh process from 81.45 to 34.81 seconds. Three requests after model startup took 23.49, 23.60 and 23.84 seconds with the short development prompt. The exact evaluation prompt took 37.05 seconds on a development photo and returned an incomplete caption. This runtime misses the interactive latency goal, so the app uses its existing encoder for live ranking. The run established cost and response-format limits for this runtime and did not produce held-out VLM relevance measurements. The saved journals and model files are external to the app.

The SigLIP 2 INT8 community conversion was evaluated on the same 150 distinct candidate photos. The model card names Google's Apache-2.0 SigLIP 2 Base as the upstream checkpoint. The precise upstream commit for the conversion was unverified. On 20 ordinary queries, CLIP returned 10 relevant top results, SigLIP 2 returned 12, and equal reciprocal-rank fusion returned 13. All three reached 16 queries with a relevant top-five result. SigLIP 2 returned five more relevant top-five slots than CLIP but put two more unjudgeable photos first. The weights alone occupy 377,991,608 bytes. Host scoring demonstrated a candidate for further comparison. Keep the current Android encoder for this build. [Official checkpoint](https://huggingface.co/google/siglip2-base-patch16-224), [paper](https://arxiv.org/abs/2502.14786), [conversion](https://huggingface.co/onnx-community/siglip2-base-patch16-224-ONNX).

MobileCLIP2 is a candidate for academic latency evaluation. Apple's released weight terms limit use to noncommercial scientific or academic research, so a future paid product needs different qualifying weights or permission. FastVLM is a candidate for selective enrichment during indexing if it can produce better visual evidence within the device budget. The authors' mobile demo uses Apple hardware. [MobileCLIP2](https://github.com/apple-aiml-research/ml-mobileclip), [weight license](https://github.com/apple-aiml-research/ml-mobileclip/blob/main/LICENSE_MODELS), [FastVLM](https://github.com/apple-aiml-research/ml-fastvlm).

The emulator workflow evidence in `app/build/semantic-demo-acceptance/receipt.json` covers 23 Android passes and 25 host passes with build and lint success. The dated result uses an actual EXIF date read from the gallery provider. The UI test opens that photo, performs example search on the cached visual index, and returns to text search. The first dated test used a provider insert field that Android replaced during scanning. The accepted run uses a JPEG with the date embedded before import.

On the same five real photos and encrypted cache, eight process-cold emulator runs compared first and repeat results. Foreground warmup reduced median first-query time from typing to a visible result from **4.845 to 2.982 seconds** with immediate input and from **2.553 to 1.568 seconds** after five seconds on the search screen. The repeat-query group medians ranged from **0.629 to 0.890 seconds** across builds. There were two process observations per build and input condition. The benchmark measured activity startup separately. The warmed build still took a median 8.719 seconds from activity start to an editable search in the immediate-input condition. These are small-sample emulator timings. `app/build/semantic-latency-ab/progress.json` records the exact APK hashes and all eight timings.

The event build adds offline **Diwali / Deepavali** resolution with Delhi calendar anchors for 2025 and 2026. `Diwali pics 2025` shows date-based candidates separately from visual suggestions. `My car at Diwali 2025` applies a confirmed-reference filter before both routes. The visual route can surface an off-date or metadata-free photo with its event date unverified. This first catalog covers two civil dates and one event. The app acceptance recorded 15 Android passes and 25 host passes at `app/build/event-demo-acceptance/receipt.json`. Controlled EXIF and off-date fixtures show the result paths work. Separate licensed festival images are needed to measure event relevance. [Event design and comparison protocol](event-photo-search-design.md) · [Exact entity model choices](exact-entity-methods.md).

The same event APK was installed on the authorized Motorola Edge 50 Pro running Android 16 with ARM64 libraries. Eight targeted Android checks passed, including CLIP retrieval, encrypted cache reopening, event candidate grouping and date filtering. With five bundled public photos, the correct photo ranked first for all five queries. Initial image indexing took 2.024 seconds, the five text queries took 0.753 seconds combined, and cache reopening decoded zero photos. ADB reported 1.081 seconds for the initial cold activity launch. The app was reopened after the tests. The fixture timings exclude personal-gallery search and UI rendering at scale. `app/build/physical-device-smoke/receipt.json` records the device, APK hash and measurements.
