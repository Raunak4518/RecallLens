# Event search on the phone

For **Diwali pictures**, search three places in parallel. Look for photos the user assigned to that event, photos with capture dates near a relevant Diwali, and photos anywhere in the indexed gallery with matching visual or OCR evidence. Combine the candidates before ranking. This retrieves a family photo taken on Diwali even if the frame contains no lamps, and it can retrieve a forwarded rangoli photo with no capture date from the visual route. Those two results need different explanations.

## Existing evidence and systems

- Google Photos documents ordinary compound searches, opt-in Ask Photos and shared-content indicators. Searching for a person by name requires a label and searching for “me” requires a self label. It is a useful comparison for query behavior and result presentation. Its documentation leaves the specific holiday matching and forwarded-photo algorithms undisclosed. [Google Photos Search](https://support.google.com/photos/answer/15235862).
- Immich documents the most directly reproducible baseline. It uses contextual embeddings and metadata in Postgres, with filters for faces, places, albums and time ranges, and separate OCR lookup. The same retrieval pattern fits the app's local encrypted index and its existing CLIP/OCR models. [Immich Search](https://docs.immich.app/features/searching/).
- Apple Photos supports dates, category terms, people and natural-language descriptions. Shared-library search can identify who added an item, which is separate from who took it. [Apple Photos search](https://support.apple.com/guide/iphone/search-for-photos-and-videos-iph392d77d5f/ios).
- The PEC authors use sets of personal photos to recognize events when an individual photo is ambiguous. PETA studies album-level recognition using CNN image features and an attention model. The useful engineering implication is to aggregate evidence across photos from the same occasion. The first Android release can do that with simple time and visual links, without running a new album model during a search. [PEC and Stopwatch HMM](https://data.vision.ee.ethz.ch/cvl/datasets_extra/pec/), [PETA paper and implementation](https://github.com/Alibaba-MIIL/PETA).

## Query resolver

Resolve the query into explicit constraints, the requested event and remaining visual terms. Keep the original text around for the search box. Use a small versioned alias table first, with exact language-aware aliases such as Diwali, Deepavali, Dipavali, दिवाली, दीपावली and દિવાળી. Resolve saved private event names before public aliases so a user can give their own event a label. Add fixed relative-year rules such as “last Diwali” meaning the most recent anchor that has already occurred in the selected locale. Ask through an inline year or region choice only when ambiguity materially changes the results.

Represent a public holiday occurrence as `eventId, year, region, localDate, zoneId, sourceUrl, revision`. Treat the anchor as a documented civil date. For example, the Delhi 2025 list gives October 20, and the 2026 central government Delhi list gives November 8. A two-day window either side is a starting retrieval choice to validate, since actual celebrations and regions differ. Let an explicit user-defined event window override the public default for that user's occasion. Derive available years from gallery date coverage and saved events. Use the fixed catalog offline. For an uncovered year, retain a visual route and display the year as unverified where appropriate. Use a relevant source rather than asking a language model to invent calendar dates. [Delhi 2025 Gazette](https://it.delhigovt.nic.in/writereaddata/Cir2024526064.pdf), [Delhi 2026 list](https://www.cgca.gov.in/ccadl/list-of-holiday), [regional observance provisions](https://rb.indianrailways.gov.in/uploads/directorate/establishment/2025/Letter_20250805_HolidaysList2026.pdf).

Keep capture, add/import and event dates as separate facts. The app's existing `GallerySource` reads `MediaStore.DATE_TAKEN` into `SelectedPhoto.capturedAtMillis`. Its explicit year filter uses device-local year boundaries and excludes missing capture dates. For a new holiday route, distinguish capture with a documented offset, provider-only dates of lower confidence, and missing dates. Resolve windows as local-date boundaries in the occurrence timezone rather than adding fixed UTC hours. Files from providers that cannot expose metadata still qualify through other evidence. A received or imported date can display a provenance clue, with year attribution based on a trusted capture timestamp, a confirmed event, or a linked duplicate with documented capture evidence. Android documents that EXIF original date and original offset are both required for a reliable epoch interpretation. [Android MediaStore columns](https://developer.android.com/reference/android/provider/MediaStore.MediaColumns#DATE_TAKEN), [EXIF date fields](https://developer.android.com/reference/androidx/exifinterface/media/ExifInterface).

## Candidate generation, evidence and ordering

1. **Confirmed event route.** Read encrypted user-confirmed membership for albums like “Diwali at home 2025” or “My engagement.” Reuse the existing concept of confirmed named references. Confirming an event photo records membership and may optionally add its capture context. Keep automatically suggested neighbors approximate until reviewed.
2. **Calendar route.** Query capture time within resolved windows. Start with approximately five civil days per occurrence and score date proximity below direct event evidence. Return date-only matches under **Around Diwali**, because ordinary meals, screenshots and documents on the same date may be unrelated. An explicit phrase like “taken on Diwali” uses the capture constraint as required and can offer visual suggestions in a separate section. The existing strict Named mode remains confirmed-only.
3. **Content route.** Search cached CLIP vectors for distinct prompts such as a family festival of lights with diyas and rangoli, and cached OCR for event aliases. Generic fireworks, candles, sweets or family gatherings match far more than Diwali. A visual match can be useful even if these cues cannot establish a specific event or year. Preserve useful query detail such as “with Dad.” If Dad is a confirmed named subject, intersect that subject's references with the relevant candidate groups. Similar-face suggestions remain a separate review action.
4. **Link duplicates and related photos.** Use the existing content hash where applicable to collapse identical copies. Evaluate a small image perceptual hash followed by a distance or embedding check for re-encoded forwards. For nearby capture times, add candidate links through supported location, confirmed people, existing album membership or close visual similarity. Bound propagation to one hop from a meaningful event anchor so a long burst or the same room cannot cause a chain reaction over the whole gallery. Expand lower-ranked ordinary photos from credible clusters when it improves recall. A forwarded duplicate can inherit suggested event evidence, with its source displayed, while adding *confirmed* event membership remains an explicit action.
5. **Merge and rank.** Intersect required constraints, union the channel shortlists, and score with a small feature vector. Useful features are confirmed membership, capture-day distance, metadata confidence, CLIP similarity, OCR alias hit, duplicate link and cluster support. Start with evidence groups ordered as **Saved event**, **Looks like Diwali** and **Around Diwali**, with direct evidence giving priority within each group. A highlighted result can have both date and visual evidence. Show **Year unknown** for an undated visual match without a trusted link. Rank within groups with deterministic rules or rank fusion for visual/OCR lists. Fit an optional lightweight per-query ranker only when genuine held-out labels justify replacing the rules.

Use date and confirmed membership lookups where possible. Compute at most a few embeddings per query, reuse cached gallery vectors, retrieve bounded candidate lists and fuse the union on a worker. The raw in-memory float cost for 10,000 × 512 dimensions is about 19.5 MiB, excluding SQLCipher, metadata, vectors for other models, runtime and application memory. Exactly scoring the cached vectors makes a useful 10k baseline before an ANN index. Report Android measurements of the actual complete app. Avoid a full image decode or generative model pass at query time. If a new model gives a meaningful gain, run it during indexing or perform a bounded second-stage check on selected candidates and measure its effect on time to first result. Existing SmolVLM2 emulator runs took roughly 24 seconds per resident development image, which places that tested runtime outside the interactive path. [Existing model measurements](semantic-search-demo.md).

| Example | Intended behavior |
| --- | --- |
| Diwali pics | Search available occurrences plus the whole-gallery appearance/OCR route. Group supported occurrence years and leave others under **Year unknown**. |
| Diwali 2025 photos of Dad | Confirmed event/year and Dad labels provide direct evidence. Date-supported candidates must match the 2025 occurrence. Strong undated scene matches with confirmed Dad can appear under **Year unverified**. Photos with trusted contradictory years should stay out of the 2025 group. |
| Photos taken on Diwali 2025 | Require a capture date within the resolved day. Offer unverified visual possibilities outside the requested result group. |
| A Diwali photo someone sent me in December | Match appearance/OCR and any duplicate link. The app can label a known import date. It can only attribute sender or chat context when a supported authorized source supplies it. |
| My sister’s wedding | Ask the user to save or confirm the wedding occurrence if unknown. Search the named person plus wedding cues, narrow with a user-confirmed date, and offer temporally linked photos from the same occasion. Generic wedding appearance cannot identify whose wedding it is. |
| The red-shirt photo with me and my car at Diwali | Apply user-confirmed identity/instance scopes first. Then combine red-shirt and event evidence, with unverified clauses visible on related suggestions. |

## 10,000-image evaluation and implementation order

1. Freeze at least **10,000 distinct, decodable real originals** with a manifest recording source, attribution and SHA-256. Use Open Images V7 for varied distractors and scale, with a separate set of licensed, manually checked event photos from Commons or attributed user-approved albums. Verify licensing per file. Public event tags are starting points for relevance review. PEC reports over 61,000 photos and EXIF for 807 albums, but distribution is by request under its agreement and the listed archive is 10.8 GB. Use it only if authorized and space permits, as a general event benchmark. The current 2,000-photo CLIP corpus is prior evidence. Qualify this new 10k run with its own manifest and receipt. [Open Images V7 metadata](https://storage.googleapis.com/openimages/web/download_v7.html), [Wikimedia Commons Dipavali source pool](https://commons.wikimedia.org/wiki/Category:Dipavali), [PEC access terms](https://data.vision.ee.ethz.ch/cvl/datasets_extra/pec/).
2. Freeze human review labels independently of model output wherever practical. Plan a held-out set of 60 or more queries covering repeated yearly holidays, private albums, forwarded copies and impossible combinations. Label event relevance, known occurrence and evidence availability separately. Include generic same-date photos, different events with fireworks or festive clothes, the same event in other years, photos with stripped metadata and year-unknown genuine photos. Keep original, forwarded and edited copies and each captured occasion in one evaluation split. Test synthetic offsets and missing EXIF as controlled stress cases of individually verified real photos. Keep those derived variants separate from the count of 10,000 distinct originals and report stress metrics separately.
3. Run date-only, visual/OCR-only and merged conditions against the same frozen gallery and relevance labels. Compare with explicit user labels separately so enrichment from human intervention stays visible. Record recall@20, precision@5, top-result success, wrong-year rate, false support on impossible requests, known-event/unknown-year results and rescue rate for relevant photos without capture evidence. Report first-stage recall against labeled positives even if a later ranker fails. Keep reviewers blind to rank and method. Publish unknown judgments separately rather than counting them as misses or successes.
4. On the emulator, measure first visible results from query entry, cache restore, warm repetitions, sustained indexing throughput, index bytes and peak memory. Break down parsing, date/OCR lookup, text encoding, ranking and UI publication. A provisional target is p95 at or below three seconds for a warm query with an existing 10k index. Measure cold start separately. Report physical phone performance separately when authorized. An emulator can establish functionality, latency on that emulator and a rough cost envelope.
5. Implement in this order. Build a catalog resolver and additive query planner under PL064, then separate result cues and confirmed event selection under PL065. Reuse the gallery's dated-access and encrypted-index behavior. Test real Android capture and missing-date paths before the 10k run under PL069 and PL071. Compare optional event recognition or language models under PL124 and PL125 after the cheap baseline. Event/10k integration remains to be implemented and measured.
