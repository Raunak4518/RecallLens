# Query execution extraction

PL064 and PL065 need one owner for query cancellation and publication. LibraryViewModel currently owns queryJob in three asynchronous branches. Nearby searches can replace its handle without cancelling the prior operation. Nearby publication checks query/photos but omits search mode, Named evidence and unavailable scope. Visual publication checks only query/mode while mixing captured image results with current Named/text state. These weak guards are not proof that a specific existing workflow has exposed a stale result, but they permit obsolete work to publish when the relevant state changes independently.

The fix was staged at .agent-staging/query while the core verifier froze app/src and models, then integrated after that baseline passed. It has not yet been compiled or tested. PhotoQueryExecution owns one job and a generation. An immediate launch cancels the previous job, increments the generation and creates a guarded PhotoQueryPublication. A publication requires the owning launch job to remain active, the same generation and an immutable PhotoQuerySnapshot matching current query, mode, gallery permission, photos/source revisions, Named library, folder/volume scope, image revision and loading state. All success and handled-error publications use that gate.

LibraryViewModel keeps query-specific orchestration and existing domain ranking/group functions. Visual ranking captures photo and embedding inputs before launching. Its publication reads the latest text evidence for that same verified source snapshot, preserving text hits completed while image ranking was active. Cached query vectors are published only when current. Clothing and nearby results use the request's evidence snapshot. This removes orphan nearby jobs and does not add service/factory layers. The established confirmed-only Named, estimated-color and related-result semantics remain unchanged.

Cache updates arriving during active visual ranking queue only the latest replacement request. Queueing increments the publication generation immediately, withholding the older ranking. The active work can finish without repeated cancellation, then its owning-job completion launches the latest queued snapshot. Text restoration/publishing also schedules this path, so newly completed OCR hits cannot be overwritten by an older visual request. Explicit query changes, refresh and clearing the ViewModel discard queued requests.

Integrated files are LibraryViewModel.kt, PhotoQueryExecution.kt and PhotoQueryExecutionTest.kt. Only query sections, the query job field/cancellations, text-update visual scheduling and coordinator composition change in the ViewModel. Five tests control completion order, include work that deliberately ignores coroutine cancellation, and verify stale success/error suppression, mode/name/scope/revision/loading changes, explicit cancellation, owning-scope cancellation, latest cached-evidence reruns and confirmed-only result grouping. They need compilation and emulator execution. Existing real clothing-screen, source-observer and pure query-plan workflows remain integration regressions.
